# Целевая модель инфраструктуры

Согласовано с пользователем 4 ноября 2026 года. Это целевой контракт и план
разработки, а не заявление о готовности всех функций. Работа и приёмка — только
на тестовом NetBox. Production не изменяем. Основную приёмку проводит пользователь.

## Сущности и связи

Одна реальная сущность должна иметь одну карточку. Selectel, ESXi, Proxmox и
pfSense дополняют её сведениями с явным происхождением.

| Ресурс | Представление | Связи |
| --- | --- | --- |
| Выделенный сервер | Device | Аккаунт/проект Selectel, площадка, гипервизор |
| Хост ESXi/Proxmox | Тот же Device | Источник Sync, кластер, гостевые VM |
| Облачная/гостевая VM | VirtualMachine | Проект, размещение, известный физический хост |
| Виртуальная pfSense | Та же VM | Интерфейсы, сети, наблюдения firewall |
| Физическая pfSense | Device | Интерфейсы и сети |
| Интерфейс, IP, подсеть, VLAN, VRF | Подходящие стандартные объекты NetBox | Подтверждённый владелец и область сети |
| Бакет, DNS-зона, DNS-запись | Отдельная понятная карточка расширения, если нет подходящей штатной модели | Аккаунт, проект, сервисы и сети |
| Глобальный роутер | Карточка маршрутизации | Полученные из API подключения, сети, подсети и маршруты |

Кластер представляет структуру виртуализации, а не произвольную группу ресурсов.
Не создаём кластер для каждого Device. Бакеты и DNS не превращаем в фиктивные VM
или устройства. Перед расширением проверяем подходящие модели установленной
версии NetBox и существующего плагина.

## Сопоставление

- Сохранённая идентичность источника или однозначное непротиворечивое аппаратное
  совпадение разрешают автоматическое связывание.
- Полное имя без других подтверждений остаётся предложением. После уточнения
  оператора 4 ноября автоматическое связывание допускается по единственному
  непротиворечивому сетевому кандидату нужного типа: назначенному публичному IP
  или свежему WAN pfSense с подтверждённым физическим хостом. Чужие привязки,
  несколько подходящих серверов и аппаратные противоречия блокируют автоматику.
- Показываем причину каждого кандидата и конфликта.
- Добавляем «Связать с существующим»: выбор подходящего Device/VM, просмотр
  последствий и одно подтверждение. Последующие сборы используют эту связь.
- Пользователь может выбрать существующую карточку даже при отсутствии кандидатов.
- По уточнённому разрешению оператора первое создание выделенного сервера
  автоматическое при каноническом UUID Selectel, свежих данных, известной
  площадке и отсутствии кандидатов/противоречий. UUID не становится serial.
  Ручное создание остаётся доступным до очередного сбора. Ресурс, явно
  отвязанный пользователем, автоматически повторно не создаётся.
- Идентичность включает провайдера, аккаунт, проект/регион при необходимости,
  тип ресурса и UUID. Совпадения разных аккаунтов не смешиваем.
- Повторная регистрация ESXi/Proxmox должна находить уже связанную физическую
  карточку, сохраняя гостевые VM и прежние идентичности.

## Поля, приоритет и размещение

Составляем поддерживаемую таблицу: поле источника → объект/поле NetBox → единицы →
владелец → поведение при отсутствии данных и удалении аккаунта.

Selectel имеет приоритет для подтверждённых сведений провайдера: названия,
конфигурации ресурса у провайдера, проекта и размещения. Для аппаратных
характеристик действует уточнённый приоритет по полям, описанный ниже.
Гипервизор сообщает структуру
виртуализации и гостей; pfSense — конфигурацию и наблюдения своих интерфейсов.
Сборщики не должны попеременно перезаписывать одно поле.

Используем стандартные поля, если совпадает их смысл: имена, состояние, модель,
серийный номер, CPU/память/диски VM, регион, площадка и сетевые объекты.
Спецификацию физического сервера храним структурированно, когда штатного поля нет.
Списки модулей RAM/дисков отображаем как компоненты, а не как число МиБ/ГиБ.
Неизвестные значения и недоступный API не стирают подтверждённые данные.
Размещение учитывает ограничения кластера, стойки и хоста; конфликт объясняем.

Технические идентичности, происхождение и исходные наблюдения сохраняем для
синхронизации и карты. В обычной карточке показываем человекочитаемую информацию;
служебные подробности отделяем от основных полей без потери доступа для диагностики.

## Единая аппаратная конфигурация Device (4 ноября 2026)

Согласован единый блок «Аппаратная конфигурация» на главной вкладке Device:
в правой колонке после Management и блока IP-адресов. Он одинаково представляет
отдельно подключённые через NetBox Sync хосты ESXi/Proxmox, серверы Selectel
и сопоставленные карточки. Кластеры не меняем и конфигурацию туда не дублируем.

- Для CPU (модель, сокеты, ядра, потоки) и памяти, видимой хосту, приоритет имеют
  данные ESXi/Proxmox. Selectel дополняет отсутствующие сведения того же смысла.
- Установленная память и состав планок могут поступать от Selectel или аппаратной
  инвентаризации хоста. Их отличаем от памяти, видимой гипервизору; количество
  планок не выводим из одного общего объёма.
- Физические диски показываем отдельной таблицей: количество, объём каждого,
  тип HDD/SSD (либо «неизвестно»). Модель и интерфейс накопителя в кратком блоке
  не нужны. Одинаковые по известным характеристикам диски группируем, разные
  показываем отдельными строками. Можно вывести общее количество дисков.
- Физические накопители, логические тома RAID и datastore/пулы храним раздельно.
  Datastore не доказывает количество физических дисков. Близкие объёмы, например
  6 ТБ у провайдера и меньшее значение у хоста, сами по себе не доказывают
  идентичность: учитываем единицы и уровень хранения. Суммарную физическую
  ёмкость не называем доступным местом после RAID.
- Существующие CPU/RAM Custom Fields сохраняем для сборщиков, фильтрации и API.
  После внедрения единого блока скрываем их дублирующее представление; другие
  пользовательские поля не затрагиваем. Единый слой представления объединяет
  поля хоста и структурированные сведения Selectel с приоритетом по параметрам.
- Сведения источников обновляются независимо, с сохранением происхождения.
  Отсутствующие поля или ошибка сбора не стирают сведения другого источника;
  ручные значения сохраняем, противоречия не маскируем объединением.

Перед реализацией проверяем фактический состав данных сборщиков: физические
диски нельзя подменять уже получаемыми datastore. Для VM сохраняем штатные
Resources и Virtual Disks. Пока зафиксировано только решение: код и данные
NetBox не меняем, реализация отложена по просьбе пользователя.

## Уточнение аккаунтов и проектов (4 ноября 2026)

Согласованная целевая схема: вложенные Tenant Groups `Selectel → Аккаунт 29916`,
Tenant — проект (например, `indeed-prod`) в группе аккаунта; Site — площадка.
Идентичность проекта определяется аккаунтом и ID провайдера, а не только именем.
Уже заполненную вручную принадлежность Tenant не перезаписываем.
Region пользователь заполняет вручную; синхронизация не должна его менять.
Существующие Regions, Sites и размещение ручных карточек пока оставляем как есть:
перестройка и миграция размещения отложены до отдельного согласования.
Это фиксация целевой схемы, а не отметка о внедрении Tenant-проекции.

## IP и основной адрес

Согласованное отображение (4 ноября 2026): в штатном Management → Primary IPv4
показываем один основной адрес. Сразу под Management нужен компактный блок
«IP-адреса Selectel» со всеми полученными адресами, отметкой основного и ссылками
на соответствующие записи IPAM. Поиск NetBox по любому из этих адресов должен
находить связанный сервер, включая адреса, не выбранные Primary.
Отображение выделенных Selectel адресов не зависит от выяснения их фактического
использования хостом или гостевой VM; это не доказательство назначения интерфейсу.
Пользователь попросил пока только зафиксировать решение: реализация этого
отображения и проверки поиска отложена, код и данные NetBox не меняем.

Выделенный провайдером адрес не обязательно назначен интерфейсу физического хоста.
Автоматическое назначение интерфейсу и выбор primary IPv4 разрешены только при
подтверждённом владельце и области сети. В противном случае сохраняем выделение
провайдером и объясняем отсутствие назначения. Адрес WAN гостевой pfSense не
становится primary IP гипервизора. Существующие чужие назначения не переносим.

## Глобальный роутинг и остальные карточки

Добавляем вкладку «Глобальный роутинг» рядом с выделенными серверами, облачными
серверами, бакетами и DNS-зонами. Сначала проверяем уже собираемые данные;
недостающий сбор реализуем в существующем сборщике. Карточки показывают все
полученные и поддержанные составляющие: сам роутер, состояние, размещение,
подключения, сети и маршруты, с указанием неполноты и времени наблюдения.
Не выдаём список роутеров за полную топологию.

Ноль означает успешно прочитанный пустой список. Ошибка доступа, неподдержанный
метод и частичный сбор отображаются отдельно. Неполный ответ не удаляет старые
ресурсы. DNS-зона раскрывает записи; бакет — доступную конфигурацию, объём и связи.
Не моделируем неизвестные связи по сходству названий.

## Контракт будущей карты

### Согласованная модель глобального роутинга (4 ноября 2026)

Выбран второй вариант: штатные объекты IPAM плюс отдельная карточка глобального
роутера расширения. Управляемый роутер Selectel не превращаем в фиктивный Device.

| Данные | Представление |
| --- | --- |
| VLAN и номер VLAN | VLAN, поле VID; имя сети используем при однозначном соответствии |
| Площадка, например SPB-2 | Site; Region остаётся отдельной ручной географической классификацией |
| CIDR подключённой подсети | Prefix |
| Имя подсети | Description Prefix, отображается рядом с CIDR |
| Шлюз | IP Address и явная связь «шлюз подсети» |
| Служебные адреса | IP Address и явные связи со своей подсетью |
| Подтверждённая изолированная область адресации | VRF |
| Исходная сеть Selectel | Сохранённая идентичность и связи с VLAN, подсетями и роутером |
| Глобальный роутер | Карточка расширения со связями с сетями и маршрутами |
| Статический маршрут | Запись расширения: роутер, сеть назначения, следующий узел |

Назначение статического маршрута не означает подключённую подсеть. Например,
`10.160.0.0/16 → 10.161.1.1` не доказывает существование подключённой сети
`10.160.0.0/24`. Сохраняем тип связи и не создаём такую сеть по одному маршруту.

В карточке роутера показываем сети, площадки, VLAN, подсети со шлюзами и служебными
IP, статические маршруты и подтверждённые связанные ресурсы. CIDR ведёт в штатную
карточку Prefix; там компактный блок «Маршрутизация Selectel» содержит ссылки на
роутер, сеть, VLAN, площадку, шлюз и служебные IP. В Device/VM предусматриваем блок
«Сетевое размещение»: IP интерфейса → подсеть → VLAN → глобальный роутер.
Не копируем в каждую карточку всю таблицу роутера; кластеры пока не меняем.

Сопоставление учитывает идентичность сети Selectel, область адресации/VRF,
IP интерфейса и принадлежность CIDR. Совпадения площадки или диапазона сами по себе
дают кандидата, но не подтверждают подключение. Один глобальный роутер может
соединять разные площадки. Существующие IP переиспользуем только при подтверждённом
совпадении области; ручные назначения и VRF автоматически не переставляем.
Для будущей карты сохраняем связи Device/VM → интерфейс → IP → подсеть → сеть →
роутер и роутер → маршрут → следующий узел, с источником и степенью подтверждения.
Автоматическое сопоставление допускается реализовать отдельным этапом.

Требования к общему поиску NetBox:

- Точный CIDR находит подсеть и/или маршрут с явным различием типов результата.
- IP шлюза или служебный адрес находит IP и связанную подсеть.
- IP существующей VM находит адрес, VM и сетевое размещение.
- Адрес, ещё не заведённый в IPAM, позволяет найти содержащую его известную
  подсеть и отдельно подходящие маршруты. Это поиск по вхождению в диапазон,
  а не только текстовое совпадение; для маршрутов учитываем область и наиболее
  специфичный префикс, не выдавая найденный маршрут за доказанный рабочий путь.
- Частичный запрос, например `10.160`, находит совпадения адресов, CIDR и маршрутов.
- Роутеры и маршруты расширения участвуют в глобальном поиске, а не только
  в поисковой строке раздела Selectel; проверяем поведение на установленной версии.

Это согласованная целевая модель, а не отметка о реализации. На данном этапе
изменяется только документация; код и данные NetBox не меняем.

Каждый узел и ребро имеют устойчивую идентичность, тип, область аккаунта/проекта/
сети, происхождение, время наблюдения и статус: подтверждено, предполагается,
устарело, конфликт. Карта получает нормализованную модель, а не парсит названия.
Прогноз последствий firewall-правил — будущая отдельная работа; маршруты, NAT,
DNS и доступность должны учитываться с явной неопределённостью.

## Жизненный цикл

Удаление аккаунта требует одного подтверждения последствий. Удаляем доказанно
созданные аккаунтом ресурсы; у прежних карточек отсоединяем данные Selectel,
сохраняя чужие ресурсы и IP. Служебные квитанции защищают от повторной старой записи.
Повторное подключение проходит через обычную форму и один первый сбор.
Сомнительный результат записи не превращаем в успех; проверяем его отдельно.

## Порядок разработки и приёмки

1. Причины несопоставленных облачных VM и понятная диагностика: identityclub.ru,
   identityconf.ru, mgate, Siena. По сообщениям пользователя причина пока неизвестна.
2. Ручное связывание и объяснение кандидатов; таблица полей и владения.
3. Конфигурация, размещение и IP: выделенный сервер и облачная VM.
4. Глобальный роутинг: сбор, нормализация, вкладка и составляющие.
5. Бакеты и DNS: понятные карточки и связи, проверка подходящих штатных моделей.
6. Повторные сборы и несколько циклов удаления/подключения обоих аккаунтов.

На каждом этапе — небольшие регрессионные тесты поведения и необходимые проверки
прав, изоляции аккаунтов, устаревшего подтверждения, повторного запроса и отката.
Основная приёмка на тестовом сервере остаётся за пользователем. Найденные дефекты
записываем с ожидаемым/фактическим результатом; факт выполнения сборщика не
подменяет проверку полноты, сопоставления и отсутствия дублей.

## Зафиксированные наблюдения пользователя

- Оба аккаунта подключились успешно; данные проектов получены.
- Ручное создание Kolmogorov работает, связь отображается.
- Нет primary IPv4 у созданного устройства; адреса видны в сведениях провайдера.
  Требуется проверить владельца интерфейса, а не безусловно назначать адрес.
- Некоторые облачные VM не сопоставлены; нужны причины для каждой строки.
- Отсутствует удобный выбор существующей карточки для ручного связывания.

Эти наблюдения не подтверждают полноту реализации или готовность production.
