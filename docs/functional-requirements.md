## REQ-001 Автоматическое создание справочников источника

Статус на 6 октября 2026: реализовано в ветке fix/requirements-001-009; автоматические проверки пройдены. Проверка реальных подключений на тестовой установке ещё требуется; production не обновлялся.

После проверки подключения единственный обязательный ручной выбор среди параметров размещения — существующая площадка, например Selectel в Санкт-Петербурге. Площадку пользователь предварительно создаёт в NetBox. Реквизиты подключения и учётные данные источника остаются необходимыми.

Терминология: пользователь назвал этот выбор «платформой». По смыслу это площадка Site. Platform в модели NetBox обозначает программную платформу, например VMware ESXi или Proxmox VE. В интерфейсе использовать понятное название «Площадка размещения», не смешивать эти понятия.

Автоматически находить и переиспользовать подходящие справочные записи; при отсутствии создавать:

- Platform по типу источника: VMware ESXi или Proxmox VE.
- Cluster Type по выбранному ранее типу источника: VMware ESXi или Proxmox VE.
- Device Role для гипервизора: Hypervisor.
- Manufacturer из данных провайдера.
- Device Type из обнаруженных производителя и модели.
- Полученные CPU, память и прочие характеристики переносить в соответствующие поля инвентаризации, не требуя ручного повторного ввода. CPU и память не являются самостоятельными типами устройств.

Использовать уже настроенный Apply Token. Отдельный временный токен для создания этих справочников в данном сценарии не запрашивать. В реализации и инструкции по установке предусмотреть права view/add для необходимых справочных моделей: текущий Apply Token такими правами на все справочники не обладает. Обычные права delete не добавлять.

Не выдумывать точную модель, высоту U или другие характеристики, которых источник не сообщает. Для общего имени Super Server предусмотреть явное представление неполных данных без обязательного ручного заполнения неизвестных характеристик. Техническое решение проверить на тестовой установке. Уточнение от 6 октября: при отсутствии производителя/модели автоматически использовать явно обозначенный тип «Оборудование не определено»; позднее оператор может выбрать точную модель.

Критерии проверки:

1. На чистом NetBox с заранее созданной площадкой источник подключается без ручного создания остальных справочников.
2. Повторная попытка не создаёт дубликаты; существующие записи сохраняются.
3. Неоднозначные совпадения объясняются пользователю; чужие объекты не присваиваются автоматически.
4. Отсутствие площадки или типа кластера не отображается как конфликт имени источника. Сейчас placement_resolution возвращает NAME_REQUIRED и при отсутствии этих зависимостей, а интерфейс показывает сообщение о конфликте имени.
5. Недостаточные права Apply Token объясняются конкретно, с указанием недостающей модели и действия.
6. Сценарии ESXi и Proxmox проверены на тестовой установке; перенос в production выполняется отдельным шагом.

## Контекст первого сценария

Источник ESXI-PAM-QA, обнаруженное имя ESXi-PAM.QA. Сервер арендован у Selectel, размещение — Россия, Санкт-Петербург; конкретный ЦОД пока не указан. Провайдер сообщил Supermicro / Super Server, AMD EPYC 7282 16-Core Processor, 767.9 GiB RAM, ESXi 6.7.0. Точная аппаратная модель и высота U не подтверждены.

## REQ-002 Раздельные учётные записи pfSense для тестовой и продовой установок

Статус на 6 октября 2026: реализовано в ветке fix/requirements-001-009; автоматические проверки пройдены. Проверка реальных подключений на тестовой установке ещё требуется; production не обновлялся.

Тестовый NetBox Sync должен создавать на pfSense отдельного локального пользователя с явным признаком Test. Рабочее имя: netbox-sync-test, описание: NetBox Sync Test. Продовая установка продолжает использовать netbox-sync с описанием NetBox Sync.

Разделить не только имена пользователей, но и каталоги коллекторов, маркеры владельца и SSH-ключи. Подготовка и повторный сбор одной установкой не должны заменять пароль, ключ, права, файлы коллектора или маркер владельца другой установки. Повторная подготовка своего подключения должна переиспользовать его ключи. Проверку владельца чужой учётной записи сохранить.

Критерии проверки:

1. На одном pfSense одновременно работают тестовое и продовое подключения под разными пользователями.
2. Подготовка и повторная подготовка тестового подключения не изменяют продовое, и наоборот.
3. Ручной сбор и сбор по расписанию работают независимо для обеих установок.
4. При конфликте владельца интерфейс показывает конкретную причину, а не общую ошибку Diagnostics: Command.
5. Миграция старого тестового подключения не удаляет и не присваивает уже созданную продовую учётку.

Временный перенос: пользователю предложено отключить старый тестовый сбор, удалить прежнего пользователя netbox-sync через User Manager и повторить подготовку из продового Sync. После повторной подготовки сбор дошёл до импорта в NetBox; после создания недостающих полей подключение стало успешным. Разделение учётных записей этим не реализовано; отключение старого расписания отдельно не подтверждено.

## REQ-003 Автоматическая подготовка первого подключения pfSense

Статус на 6 октября 2026: реализовано в ветке fix/requirements-001-009; автоматические проверки пройдены. Проверка реальных подключений на тестовой установке ещё требуется; production не обновлялся.

Первое подключение pfSense должно проходить без ручных команд в контейнере NetBox и без ручного создания служебных полей. Включить необходимые поля в автоматическую подготовку NetBox и проверять их готовность перед первым импортом:

- pfsense_inventory — JSON, подпись «Сервисы и правила pfSense».
- pfsense_network — JSON, подпись «Сеть pfSense».
- Оба поля привязаны только к virtualization.virtualmachine, группа NetBox Sync, required=False, ui_visible=hidden, ui_editable=no, как ожидает текущий Guard.

Предусмотреть необходимые права при первоначальной настройке, чтобы обычный Apply Token мог выполнять импорт после подготовки. Не требовать от оператора устранять HTTP 403 вручную. Конкретный механизм подготовки выбрать при реализации: первоначальный onboarding или ограниченная операция подготовки Guard. Не выдавать без необходимости постоянные широкие права и не добавлять обычные права delete.

Существующие совместимые поля переиспользовать без изменения данных. Несовместимый тип или привязку объяснять явно, не перезаписывать молча. Повторная подготовка, повторный импорт и восстановление после частичной ошибки не должны создавать дубликаты или менять пароль и ключ уже подготовленной своей учётки.

Ошибки разделять по этапам: TLS и доверие CA, вход и Diagnostics: Command, конфликт владельца учётки, SSH и соответствие VM, импорт в NetBox. Показывать конкретную причину отказа Guard, включая недостающие поля и права, без раскрытия секретов. Не отключать проверку TLS автоматически.

Если учётка и сбор уже подготовлены, а импорт завершился ошибкой, сохранять подтверждённый этап и позволять повторить сбор/импорт без повторного ввода административного пароля pfSense, когда сохранённого SSH-доступа достаточно.

Критерии проверки: чистая установка; совместимые существующие поля; несовместимые поля; недостаточные права; повтор после ошибки импорта; повторный ручной сбор; последующий сбор по расписанию; отсутствие вмешательства в другую установку Sync согласно REQ-002.

Подтверждённый результат текущего ручного обхода: в продовом NetBox оба поля отсутствовали (вывод []), импорт возвращал HTTP 403. После их создания локально в NetBox пользователь подтвердил успешное подключение. На скриншоте pfSense (#252) в PVE-INFRA-TEST имеет статус Connected, последний сбор 4 октября 2026 года в 16:19:30, автоматический сбор включён. Выполнение следующего запуска по расписанию пока не проверено. Вторая VM Service - pfSense (#214) в ESXI-PAM-QA остаётся Not connected.

## REQ-004 Читаемое отображение служебных полей после чистой установки

Статус на 6 октября 2026: реализовано в ветке fix/requirements-001-009; автоматические проверки пройдены. Проверка реальных подключений на тестовой установке ещё требуется; production не обновлялся.

Пользователь сообщил, что в production на виртуальных машинах снова показываются сырые JSON-поля, хотя на тестовой установке отображение корректное. Скриншот подтверждает Source identities (sync_identities) и Original source names (sync_original_names) в стандартном блоке Custom Fields одновременно с читаемой панелью Guard «NetBox Sync — сведения об источнике». Также видны пустые Guest architecture, Guest kind, Provider guest OS hint и Container swap. Description пользователь проверил: работает, менять его в рамках этой проблемы не требуется.

Причина по текущему коду: netbox_sync/prerequisites.py definition() создаёт поля без ui_visible и ui_editable. Настройка скрытия JSON существует отдельно в команде Guard configure_sync_display; наличие панели Guard само по себе не скрывает стандартные поля. Необходима автоматическая согласованная настройка отображения при первоначальной подготовке и обновлении, а не отдельный ручной шаг после каждой чистой установки.

Требования:

- Скрывать служебные JSON, представленные читаемыми панелями Guard, из стандартного блока Custom Fields. Идентификаторы показывать при необходимости в сворачиваемом техническом разделе панели.
- Сохранять сами поля, JSON, принадлежность источникам и доступ через API; не удалять данные ради внешнего вида.
- Пустые дополнительные характеристики не показывать; полезные заполненные характеристики сохранять в понятном виде.
- Настройки отображения применять автоматически после создания полей и установки необходимых шаблонов Guard; корректно обрабатывать уже существующие поля без изменения пользовательских посторонних полей.
- Проверить чистую установку и обновление, VM и устройства обоих провайдеров, интерфейсы и pfSense; исключить дублирование данных между стандартными полями и панелями.
- Проверить сохранение Description и отсутствие регрессий после повторной синхронизации.

5 октября 2026 года пользователь разрешил реализацию исправления JSON: сначала репозиторий и проверки, затем применение на production с предварительной резервной копией. Продовые настройки пока не изменены.

Исправление первого создания полей отправлено в main, коммит c358be6: JSON сразу hidden, остальные наблюдения if-set, ручное редактирование служебных полей выключено. Версия контракта подготовки повышена до 4. Проверки: 28 passed, 14 skipped (платформенные Linux/root проверки). Для существующего production предусмотрено применение уже установленной команды Guard configure_sync_display --apply после бэкапа БД. Она скрывает пять JSON-полей, не меняя значения; пустые скалярные поля существующей установки эта команда не меняет. Новые defaults требуют установки Sync из исправленной версии; одно скачивание исходников не обновляет работающий образ. Продовое применение и визуальная проверка пока ожидаются. Дальнейшее согласование отображения существующих скалярных полей остаётся открытым.

Результат применения на production 5 октября 2026 года: пользователь прислал успешный вывод configure_sync_display --apply. esxi_host_network, physical_disks, sync_identities, sync_network_observations и sync_original_names переведены из always в hidden; команда подтвердила сохранность JSON. Бэкап: /netbox/backups/before-json-display-20261005-123951. Исходники на VM netbox переключены на c358be6. Визуальная проверка страниц и проверка после следующей синхронизации пока ожидаются; работающий образ Sync этим не обновлялся.

## REQ-005 Структурированная таблица сведений об источнике и дисках

Уточнение от 6 октября 2026 года: требование переработать таблицу физических дисков отменено и заменено REQ-008 — убрать отображение и прекратить сбор. Описание ниже сохранено как история, не как задание на реализацию таблицы дисков.

Статус на 6 октября 2026: отменено уточнением REQ-008 — вместо переработки скрывается вся панель сведений об источнике на Device.

Переработать панель Guard «NetBox Sync — сведения об источнике», особенно физические диски. Цель — компактная, понятная, структурированная таблица вместо длинного списка повторяющихся «№1 / ...». Тип показывать первым. Для устройства выводить последнюю часть пути; полный путь сохранять доступным в деталях или подсказке. Не повторять номер диска на каждой строке, убрать избыточное дублирование размеров и других значений. Представлять диски строками с понятными столбцами или компактными группами; точный вариант выбрать при реализации. Идентификаторы синхронизации оставить в отдельном сворачиваемом техническом разделе. Исходные данные не менять и не терять.

Проверить светлую и тёмную темы, длинные значения и отсутствие данных.

## REQ-007 Расписание на точное московское время

Статус на 6 октября 2026: реализовано в ветке fix/requirements-001-009; автоматические проверки пройдены. Проверка реальных подключений на тестовой установке ещё требуется; production не обновлялся.

В редакторе расписания сохранить интервальный режим (каждые N минут/часов) и добавить отдельный режим запуска в заданное время по Москве. Поддержать ежедневный запуск с выбором HH:MM (например 00:00 или 18:00), еженедельный с выбором дня недели и времени, ежемесячный с выбором числа и времени. Явно показывать режим и часовой пояс Europe/Moscow (MSK), а также ближайший запуск с датой и временем.

Вычислять расписание в Europe/Moscow независимо от часового пояса ОС/контейнера; хранить моменты запуска в UTC. Проверять корректность серверных часов/синхронизации времени и показывать проблему при обнаруженном отклонении, не изменяя системные часы автоматически. При реализации определить и явно описать правила для пропущенного запуска после простоя, отсутствующего числа месяца и перекрытия долгих запусков; не запускать одну синхронизацию одновременно дважды. Интервальный режим отсчитывается от согласованной точки запуска/сохранения, которая должна быть понятна в интерфейсе.

Критерии проверки: ежедневные 00:00 и 18:00 MSK; недельное и месячное расписание; сервер в UTC и в MSK даёт один и тот же момент запуска; перезапуск сервиса не сдвигает заданное время; сохранение существующих интервальных расписаний без изменения их поведения.

## REQ-008 Убрать таблицу физических дисков устройств и прекратить сбор

Статус на 6 октября 2026: реализовано в ветке fix/requirements-001-009; автоматические проверки пройдены. Проверка реальных подключений на тестовой установке ещё требуется; production не обновлялся.

Основание: скриншот панели «NetBox Sync — сведения об источнике» на странице Device. В разделе «Физические диски» показаны путь устройства, тип, модель, состояние, серийный номер и размер дисков ESXi. Запрос пользователя: «эту таблицу убрать и эти данные не собирать».

Требования:

- Убрать таблицу физических дисков со страниц устройств NetBox.
- Прекратить сбор и запись этих сведений о физических дисках хостов в `physical_disks`, включая ручную синхронизацию и запуск по расписанию. Не ограничиваться скрытием таблицы при продолжающемся сборе.
- Проверить все провайдеры, которые заполняют эти сведения; исключить повторное появление таблицы и данных при следующей синхронизации или новой установке.
- Не распространять отказ от физических дисков хоста на виртуальные диски VM, их ёмкость и другие независимые данные без отдельного уточнения.
- Служебные идентификаторы, необходимые для сопоставления объектов и контроля принадлежности, не удалять вместе с представлением: скрытие панели и прекращение сбора необязательных характеристик не должны нарушить работу синхронизации.

Уточнение пользователя от 6 октября 2026 года: **скрыть всю панель «NetBox Sync — сведения об источнике» на устройствах**, включая исходные имена и раскрываемые идентификаторы. Внутренние идентификаторы сохранить для синхронизации. Ранее сохранённые значения физических дисков остаются скрытыми; удаление не согласовано.

## REQ-009 Занятость подсетей и резервирование IP в NetBox

Статус на 6 октября 2026: реализовано в ветке fix/requirements-001-009; автоматические проверки пройдены. Проверка реальных подключений на тестовой установке ещё требуется; production не обновлялся.

Цель: из устройства или кластера быстро открыть конкретную сеть, найти владельца IP и выбрать адрес для новой машины, не смешивая одинаковые адреса из независимых сетей и не обещая недоказанную доступность.

Уточнения пользователя от 6 октября: данные устаревают через два интервала сбора pfSense; резервирование доступно при штатном праве NetBox на добавление IP-адресов; связь LAN с подсетью/VRF подтверждается один раз вручную.

### Интерфейс и способ расширения

- В интерфейсе NetBox добавить переход «Сети» со страницы Device/Cluster. Далее: сеть/LAN и её подсеть → список адресов и диапазонов. Предпочтительно расширить установленный плагин Guard штатными представлениями и шаблонами NetBox; не править ядро NetBox.
- На странице выбранной подсети разместить кнопку «Зарезервировать IP», также доступную для выбранного адреса-кандидата. Это предлагаемая новая функция, её пока нет в нашей установке.
- REST API служит для работы с данными; собственные страницы, формы и кнопки создаются кодом плагина. Сам по себе API не добавляет произвольный UI. Простые переходы можно делать Custom Links, но операция резервирования требует серверного обработчика.
- Показывать контекст сети, подсеть, шлюз, DHCP-пул, связанные хосты, время и полноту последнего сбора. Столбцы: IP/диапазон, состояние, устройство/VM, основание, время наблюдения. Ссылки ведут к соответствующим объектам.
- Последовательные адреса с одинаковым состоянием объединять в диапазоны; отдельный адрес показывать отдельно. Фильтры: кандидаты для выдачи, назначенные, резервы, DHCP, конфликты. Поиск внутри сети; при глобальном поиске обязательно показывать сетевой контекст каждого совпадения.

### Модель и сбор данных

- Использовать штатные NetBox Prefix, IP Range, IP Address и VRF. Независимые пересекающиеся адресные пространства разделять VRF по подтверждённой топологии; не создавать отдельную сеть автоматически на каждый хост. Общая LAN нескольких гипервизоров учитывается совместно.
- Подсеть определять по адресу/маске интерфейса pfSense, не по границам DHCP-пула. Подтвердить соответствие интерфейса pfSense мосту/port group/VLAN гипервизора. Имена LAN, совпадение IP или MAC сами по себе недостаточны для объединения сетей.
- Сопоставлять VM и интерфейсы по устойчивым идентификаторам в контексте источника. Не использовать имя VM или глобально уникальный MAC как единственное основание.
- Объединять назначения и резервы NetBox, IP интерфейсов VM/хостов, адреса шлюзов и VIP pfSense, DHCP-пулы, статические DHCP-привязки, активные аренды и дополнительные ARP-наблюдения. Учитывать устройства всей сети, включая находящиеся вне выбранного кластера.
- В текущем проверенном сборщике есть интерфейсы/маски, VLAN, DHCP-пулы и статические IPv4-привязки; сбор активных аренд и ARP необходимо добавить. Проверить полноту поддержки применяемого DHCP backend, дополнительных пулов и VIP перед оценкой доступности.
- DHCP-пул целиком исключать из кандидатов для ручной статической выдачи, даже при отсутствии активных аренд. Согласовать модель диапазона с хранением отдельных IP: NetBox Mark populated запрещает создание IP внутри диапазона, поэтому этот флаг нельзя включать без учёта выбранной модели аренд.

### Достоверность и резервирование

- Различать: назначен/наблюдался, зарезервирован, DHCP-пул, конфликт, не обнаружено использования, недостаточно данных. Отсутствие записи не называть гарантированно свободным адресом.
- Выключение VM, отсутствие ping/ARP и истечение аренды не освобождают адрес автоматически. Неполный/устаревший сбор, неизвестная привязка сети и неразрешённые наблюдения не должны давать ложный зелёный статус. Исключать служебные адреса с учётом типа и маски сети.
- Форма резервирования: выбранные сеть и IP, назначение/описание, при необходимости будущая VM. Показывать основание выбора и свежесть данных.
- Сервер повторно проверяет область, доступность по известным данным и права пользователя, затем создаёт штатный IP Address со статусом Reserved. Проверка и запись должны предотвращать конкурентную выдачу одного адреса в одной области; повтор запроса не создаёт дубликат. Проверить взаимодействие с обычными API/UI-записями NetBox.
- Выполнять изменение только подтверждённым POST с защитой CSRF, проверкой прав пользователя и журналированием автора. Не раскрывать Apply Token в браузере и не обходить права viewer через служебный токен.
- Резервирование в NetBox не меняет DHCP/pfSense и не назначает IP гостевой ОС. Для надёжного учёта новые статические назначения должны проходить через резервирование; неизвестное ручное назначение вне учёта исключить одной синхронизацией невозможно.

### Проверка первого сценария

Сначала тестовая установка и одна подтверждённая сеть PVE-INFRA-TEST. Проверить: одинаковый IP в разных VRF; общую LAN нескольких хостов; статический IP вне DHCP-пула; выключенную VM; аренду и DHCP-резерв; VIP; неполный и устаревший сбор; конфликт IP; одиночного кандидата и диапазон; два одновременных запроса резервирования; повтор запроса; права viewer. Резервы не затираются последующей синхронизацией. Production — после проверки, отдельным обновлением.

Вопросы для пилота: какая LAN/подсеть PVE-INFRA-TEST берётся первой и какие другие устройства/гипервизоры входят в неё; какие роли могут резервировать IP; какой срок считать допустимой свежестью данных и как оформлять освобождение резерва. Автоматическое удаление резервов по таймеру пока не согласовано.

## REQ-010 Подготовить NetBox Sync и NetBox Guard к NetBox Map

Дата: 6 октября 2026 года. Статус: архитектурное направление одобрено пользователем, задачи записаны; реализация и развёртывание не выполнены. Сейчас пользователь поручил документирование, а не изменение кода или установок.

Основание и согласованная архитектура: [NetBox Map и подготовка данных NetBox](netbox-map-decisions.md). Под плагином понимается уже установленный NetBox Sync Guard внутри NetBox; отдельное приложение NetBox Sync отвечает за сбор. Новый плагин и отдельную базу графов на начальном этапе не создавать.

### Задачи NetBox Sync

1. Проверить и дополнить связи хост → VM → интерфейс → сеть и соответствие сетевых интерфейсов pfSense. Передавать подтверждённые связи и сведения о неполноте; не определять общую сеть только по имени LAN, IP или MAC. Учитывать независимые адресные пространства согласно REQ-009.
2. Использовать устойчивые идентификаторы в контексте источника. Переименование хоста/VM не должно менять идентичность или создавать дубликаты; сохранять принадлежность существующих объектов.
3. Подготовить структурированные данные для общего слоя чтения Guard: стандартные объекты NetBox для оборудования, VM, интерфейсов и IPAM; типизированные Custom Fields для дополнительных характеристик; проверяемая структура специфических данных провайдера.
4. Дополнить сбор pfSense для полного просмотра и последующей оценки правил: порядок, интерфейсы/направления, firewall, NAT, aliases, маршруты, расписания и автоматически сформированные правила. Сначала инвентаризировать пробелы текущего сборщика. Для неподдерживаемых или недоступных данных явно передавать ограничение вместо пустого успешного результата.
5. Сохранять источник и время наблюдения данных. Ручная синхронизация и расписание должны формировать одинаковую по смыслу структуру. Не дублировать сбор в будущей Map.

### Задачи NetBox Guard и представления NetBox

1. Создать общий слой чтения и версионируемый документированный API объектов и связей для панелей NetBox и Map. Не использовать HTML, подписи таблиц или их порядок как контракт данных. Свести различия форматов ESXi, Proxmox и pfSense в этом слое, чтобы Map не повторяла их разбор.
2. Сделать Device основной понятной карточкой гипервизора: оборудование, Primary IP, VM, интерфейсы, сети, связанные pfSense, свежесть и состояние синхронизации. Подробности раскрывать по ссылкам/разделам без необходимости искать их в разных несвязанных таблицах.
3. Cluster оставить логической группировкой со сводкой хостов, VM и выделенных ресурсов. Не дублировать характеристики Device. Физические ресурсы, выделенные ресурсы и загрузку явно различать; не вычислять загрузку из суммы vCPU.
4. Существующие кластеры, их принадлежность и привязки сохранить. Удаление кластеров или массовая миграция VM на прямую привязку к Device не согласованы этим требованием.
5. Сохранить машиночитаемость существующих `esxi_host_network`, `pfsense_network`, `pfsense_inventory`, независимо от скрытия сырого JSON. Конкретные миграции хранения определить при реализации с сохранением данных и совместимости потребителей.
6. Обеспечить доступ ко всем собранным правилам pfSense: ограничение таблицы первыми 100 строками не переносить в полноту API или расчёта. Различать отсутствие правил, недоступность раздела и неполный сбор.
7. API должен отдавать устойчивые идентификаторы, связи, источник, время и известные ограничения данных. Переименование и изменение оформления не должны нарушать работу Map. Сохранять действующие ограничения доступа NetBox/Guard при добавлении новых представлений.

### Требования к будущей Map и анализу

- Отдельные связанные режимы «Размещение» и «Сетевой доступ». Первый показывает иерархию; второй — путь конкретного обращения и относящиеся к нему правила. Не смешивать факт размещения с прохождением трафика. В одной LAN обращение может обходить pfSense.
- Хранить настройки расположения значков и масштаба отдельно от инфраструктурных фактов. Map читает сведения через NetBox API.
- Анализ обращения: источник/VM, назначение, протокол, порт; объяснение пути, влияния firewall и NAT. Результат — разрешено по конфигурации, заблокировано или недостаточно данных, с основанием. Не приравнивать разрешение правила к доступности приложения или интернета.
- Предположительно лишнее правило — объяснимый кандидат на проверку, без автоматического удаления.
- Будущий симулятор сравнивает исходный и изменённый сценарии; изменения правил остаются в сценарии. Применение к production pfSense не входит в функцию: пользователь вносит реальное изменение самостоятельно.

### Последовательность и критерии приёмки

Первый этап: тестовая установка, PVE-INFRA-TEST и его pfSense. Проверить полный путь от Device до VM, интерфейса и подтверждённой сети, карточку хоста и общий контракт данных. Далее — полнота правил и объяснение обращений; затем Map и моделирование.

Проверки для возвращения к реализации:

1. Одна VM видна в карточке хоста и API как один и тот же объект; переименование не создаёт дубликат. Повторная синхронизация без изменений не размножает объекты и связи.
2. Совпадающие имена/IP/MAC в независимых сетях не объединяют объекты. Общая сеть нескольких хостов не разделяется произвольно по устройствам.
3. Перестановка столбцов, перевод подписей и скрытие JSON в UI не меняют машинный контракт и результат чтения Map.
4. На Cluster показана сводка, на Device — характеристики хоста; выделенные VM ресурсы не подписаны как физическая ёмкость или загрузка.
5. При неполном/неуспешном сборе не появляются ложные выводы «правил нет», «адрес свободен» или «доступ разрешён». Видны источник и свежесть данных.
6. Более 100 правил доступны полностью через предусмотренный способ чтения; обработка большого списка не ограничивается первыми строками UI.
7. Для поддерживаемых сценариев firewall/NAT показано объяснение результата, для неподдерживаемых — ограничение. Проверить обращение внутри LAN без pfSense, NAT, порядок правил и влияние расписания; границы поддержки зафиксировать до заявления о готовности анализатора.
8. Моделирование не меняет текущие данные инфраструктуры и конфигурацию firewall. Результат допускает «недостаточно данных» и не обещает доступность сервиса на основании одного allow-правила.

REQ-006 по читаемости pfSense и REQ-009 по IPAM выполнять согласованно с этим требованием. REQ-008 по прекращению сбора физических дисков сохраняет силу; возвращать этот сбор ради Map не нужно. Конкретные URL API, миграции и детали реализации ещё не выбраны и не являются выполненными работами.
