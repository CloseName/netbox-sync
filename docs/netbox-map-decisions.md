# NetBox Map и подготовка данных NetBox

Дата начала обсуждения: 6 октября 2026 года.

Документ содержит цели и архитектуру будущей NetBox Map, одобренные пользователем 6 октября 2026 года. Статус: согласовано для будущей реализации; код, сборки и работающие установки в рамках записи решений не изменялись. Новые гипотезы и варианты добавлять только после подтверждения пользователя.

## Подтверждённые цели

1. Подготовить данные NetBox и работу NetBox Sync к использованию будущей NetBox Map. Map должна получать сведения из NetBox и обновлять схему вслед за изменениями этих сведений.
2. Обеспечить понятное, структурированное и управляемое представление инфраструктуры. Пользователь должен быстро понимать, где расположен хост, какие VM и сети с ним связаны и как устроены сетевые обращения.
3. Устранить путаницу между сведениями на страницах Device, Cluster и виртуальных машин. Основная карточка физического хоста — Device; Cluster остаётся логической группировкой со сводкой. Удаление существующих кластеров и миграция привязок VM не входят в принятое решение.
4. Обеспечить устойчивый программный доступ к данным, включая сведения, которые сейчас отображаются собственными таблицами и Custom Fields. Будущие изменения оформления не должны требовать переделки логики извлечения данных Map.
5. Представлять сетевую инфраструктуру на удобной схеме с возможностью последовательно раскрывать детали. Указанная пользователем схема Indeed-Infra.drawio служит ориентиром для обсуждения, а не обязательным шаблоном или полной моделью инфраструктуры.
6. Предусмотреть отображение правил firewall и NAT всех подключённых pfSense. На схеме должно быть понятно, какая VM, по какому протоколу и порту, куда обращается и какие правила влияют на это обращение.
7. Помогать пользователю разбираться в причинах разрешения и ограничения доступа, а также замечать возможные лишние или отсутствующие правила. Информация должна быть достоверной и не вводить пользователя в заблуждение.
8. В перспективе предусмотреть моделирование изменения правила или порта до ручного внесения изменения на production pfSense. Пользователь описывает предполагаемое изменение и проверяемое обращение, получает объяснение ожидаемого результата, затем самостоятельно принимает решение о реальном изменении.
9. Начать с обсуждения основы данных и представления информации. Сейчас не менять работающие установки, не строить всю Map и не применять изменения правил firewall.

## Ответственность компонентов

| Компонент | Ответственность |
| --- | --- |
| NetBox Sync | Сбор данных ESXi, Proxmox и pfSense, сопоставление объектов и синхронизация с NetBox. |
| NetBox и установленный NetBox Sync Guard | Хранение данных, понятные карточки, общий слой чтения объектов и связей, API для Map. Далее в документе плагин называется NetBox Guard. |
| Будущая NetBox Map | Схема инфраструктуры, объяснение сетевых обращений и в дальнейшем моделирование предполагаемых изменений. |

Расширять существующий NetBox Guard. Отдельный новый плагин и отдельная база графов для начального этапа не требуются. Map получает инфраструктурные сведения через NetBox; повторный сбор с гипервизоров и pfSense внутри Map не создавать.

## Карточки хоста и кластера

Device является основной точкой входа для физического гипервизора: характеристики оборудования, адрес управления, размещённые VM, интерфейсы, сети, связанные pfSense, состояние и время синхронизации.

Cluster показывает состав хостов и VM, сводные выделенные ресурсы и ссылки на подробности. Характеристики одного сервера не копировать в Cluster. Различать физическую ёмкость, выделенные VM ресурсы и фактическую загрузку. Выделенные vCPU не приравнивать к физическим ядрам или текущей загрузке CPU.

Существующие кластеры сохраняются. Возможность прямой привязки VM к Device не означает согласования массовой миграции: перед её отдельным рассмотрением потребуется проверить принадлежность объектов и логику синхронизации.

## Хранение и общий доступ к данным

| Категория | Принятое направление |
| --- | --- |
| Device, VM, интерфейсы, IP, подсети, VLAN, VRF | Стандартные объекты NetBox. |
| Дополнительные характеристики оборудования | Типизированные Custom Fields, например модель CPU. |
| Специфическая топология виртуальных коммутаторов и правила pfSense | Проверяемые структурированные данные плагина. |
| Координаты значков, масштаб и свёрнутые группы | Настройки Map, отдельно от инфраструктурных фактов. |

Создать в NetBox Guard общий слой чтения данных для панелей NetBox и API Map. Оформление HTML-таблиц не является форматом обмена. API отдаёт документированные объекты и связи, имеет версию формата и не заставляет Map самостоятельно разбирать разные схемы каждого провайдера.

Объекты и связи имеют устойчивую идентификацию, источник сведений и время наблюдения. Переименование не создаёт новый объект карты. Совпадение имени, IP или MAC в независимых сетях не объединяет объекты. Связи включают размещение VM на хосте, подключение интерфейса к сети и назначение IP интерфейсу; неподтверждённые связи не выдавать за установленные.

Существующие структурированные поля служат исходной основой: `esxi_host_network` на Device, `pfsense_network` и `pfsense_inventory` на VM. Скрытые JSON-поля остаются доступны через API; изменение их отображения не должно менять смысл данных. Подготовка Map не требует возвращать сырые JSON на страницы.

## Представление инфраструктуры

Предусмотреть два связанных режима: «Размещение» и «Сетевой доступ».

Размещение раскрывает площадку, хосты, VM и подключённые сети. Древовидное представление используется для удобства навигации. Сетевые связи могут соединять разные ветки: сеть не ограничивать деревом размещения.

Сетевой доступ показывает путь выбранного обращения. Пользователь выбирает VM и назначение; подсвечиваются относящиеся к обращению интерфейсы, сети, переходы и правила. Все возможные обращения одновременно не рисовать. VM в одной LAN могут общаться без pfSense; наличие общего firewall само по себе не означает прохождения трафика через него.

## Правила pfSense и объяснение доступа

Доработать сбор и представление правил firewall/NAT всех подключённых pfSense. Для достоверной оценки учитывать порядок, интерфейс, направление, aliases, NAT, маршруты, расписания и особенности обработки соединений.

Текущая основа не считается полным анализатором политики: автоматически сформированные правила не собираются, часть aliases исключена, топология может быть неполной. Ограничение текущего отображения первыми 100 строками не должно ограничивать API Map и доступ пользователя ко всем собранным правилам. Полноту данных показывать явно.

Различать результаты «Разрешено по собранной конфигурации», «Заблокировано» и «Недостаточно данных». Для результата показывать основание: правило, преобразование NAT, путь или недостающее условие. Разрешение firewall не подтверждает работающий сервис, обратный маршрут или фактическую доступность интернета. Предположительно лишние правила показывать как кандидатов с объяснением, а не как указание на автоматическое удаление.

## Моделирование изменений

После подготовки данных и объяснения текущих обращений предусмотреть отдельный сценарий: выбор VM, назначения, протокола и порта, добавление предполагаемого изменения правила, сравнение результата до и после.

Сценарий не меняет реальную конфигурацию pfSense. Пользователь принимает решение и вносит изменение на production вручную. При неполных данных или неподдерживаемом поведении не обещать успешное соединение.

## Последовательность реализации

1. На тестовой установке проверить связку PVE-INFRA-TEST: хост → VM → интерфейсы → сети → pfSense. Подготовить общий формат объектов и связей и удобную карточку хоста.
2. Дополнить сбор pfSense, обеспечить просмотр правил и объяснение конкретных сетевых обращений.
3. На проверенной основе реализовать Map и затем моделирование изменений. Промежуточное изображение топологии может использоваться для проверки связей; оно не подтверждает корректность симулятора.
