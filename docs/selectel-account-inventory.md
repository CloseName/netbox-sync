Проверенная исходная ревизия: `05be5536d8aa9e677a78f8fc5b6b3a528f4a9071`.

## Реализован первый шаг: аудит 0.4.0

Добавлен общий отчёт `account.json` и таблица продуктов в `report.html`. Реестр
охватывает 20 групп, отдельно показывает возможности адаптеров и результаты
запросов по проектам/регионам. Пустой успешный список, отказ доступа, неполный сбор,
отсутствие каталога, исключение профилем и отсутствие адаптера различаются.
Неизвестные сервисы каталога видны отдельно, без попыток обратиться к их API.

Числа обозначают наблюдения отдельных коллекций; общего счётчика уникальных

`deploy/audit-selectel-account-test.sh ACCOUNT` собирает из текущей ревизии отдельный
контейнер и запускает профиль `all` только на тестовом хосте. Запрашивает IAM-токен
или данные сервисного пользователя через скрытый ввод. Не обращается к NetBox,
не перезапускает сервисы, не создаёт apply-команды и не добавляет расписание.
Авторизация может выпускать project-scoped токены; операции над ресурсами — чтение.

## Второй шаг: аудит 0.5.0

Профиль `all` теперь читает RRsets каждой доступной зоны Selectel DNS: имя,
тип, TTL и значения записей. Для Swift-контейнеров читает статистику, тип доступа,
квоты, настройки веб-публикации и домены через региональный Object Storage API.
Файл `dns-storage.json` содержит эти сведения с account/project/region и ID
родительской зоны либо именем контейнера; отдельный статус сохраняется для каждого
запроса. Неизвестные поля ответа отбрасываются до экспорта. Известные секреты
авторизации редактируются; значения DNS TXT сохраняются как часть конфигурации,
поэтому отчёт следует считать внутренним инвентарным документом.

Одинаковые имена контейнеров в разных проектах не объединяются. Суффикс
`_s3multipartuploads` остаётся только подсказкой, не доказательством типа ресурса.
Адрес управления выбирается из каталога того же проекта и региона. Отсутствующий,
неоднозначный или недоверенный адрес даёт диагностику, а не обращение к случайному API.
Добавлены только документированные точные узлы Swift UZ/KZ и API UZ. Частные
узлы selprivate.ru и расходящийся с документацией адрес управления KZ не разрешены.

Не собираются объекты бакетов, их список, журналы и сертификаты, S3 versioning,
lifecycle и policy API. Kubernetes и БД пока без адаптеров. Переноса DNS/S3
в NetBox и расписания этим этапом не добавлено. Запуск тем же тестовым скриптом
не меняет Selectel-ресурсы, NetBox, IP управления и назначения pfSense.

Контракт возможностей повышен до версии 2: один успешно прочитанный список зон
или контейнеров больше не означает успешного сбора их деталей. Исправлена также
классификация аккаунта: технические IAM/Resell-записи каталога проектов не портят
статус отдельных успешных запросов аккаунта.

Источники API: [DNS](https://docs.selectel.ru/api/dns-actual/),
[Object Storage](https://docs.selectel.ru/api/object-storage/),
[адреса API](https://docs.selectel.ru/api/urls/).

## Цель и границы

Пользователь подключает аккаунт один раз. Система обнаруживает доступные проекты,
регионы и ресурсы поддерживаемых продуктов, обновляет их по расписанию и показывает
связи, происхождение сведений и пробелы сбора. Новые экземпляры поддерживаемых
ресурсов обрабатываются без отдельных скриптов и привязок к конкретным серверам.

Новый продукт или несовместимая версия API могут потребовать нового адаптера.
Присутствие сервиса в каталоге не означает, что адаптер может получить его ресурсы.
Неизвестный сервис показывать как неподдерживаемый; не обещать чтение неизвестных
ресурсов и не отправлять токены на произвольные адреса из ответа API.

«Все данные» здесь — инвентарные сведения о ресурсах, конфигурация и связи.
Не собирать содержимое S3-объектов, данные внутри БД, пароли, приватные ключи,
kubeconfig, содержимое Secrets Manager, пользовательские файлы и скрипты запуска.
Для каждого продукта нужны разрешённые поля до сохранения ответа, ограничения
объёма, пагинация и проверка отсутствия секретов. Неизвестные поля не сохранять
автоматически целиком ради совместимости.

## Как представлять ресурсы

В NetBox использовать стандартные объекты там, где совпадает смысл. Остальное
показывать отдельными карточками ресурсов провайдера с фильтрами, API, историей
и ссылками на стандартные объекты; не создавать custom field на каждый ключ API.

| Ресурс | Инвентарные сведения | Представление и связи |
|---|---|---|
| Аккаунт / проект | ID, имя, область доступа, регионы, покрытие, время сбора | Карточки интеграции; Tenant не создавать по одному совпадению имени |
| Dedicated | UUID, конфигурация, размещение, состояние услуги, порты и выделенные сети | Device независимо от наличия гипервизора; отдельные связи выделения IP и фактического назначения |
| Cloud VM | UUID, имя, состояние, flavor, vCPU/RAM, размещение, NIC, диски | VirtualMachine и VMInterface; физический хост провайдера не выдумывать |
| Диски / snapshots / images | ID, размер, тип, состояние, attachment/source IDs | Реестр; VirtualDisk только при корректной однозначной принадлежности VM, multiattach учитывать отдельно |
| Сети | Network/subnet/port IDs, адреса, VLAN/VRF-контекст, роутеры, правила | IPAM и интерфейсы при доказанной области/принадлежности; overlay ID не превращать в VLAN ID |
| DNS | Zone ID/name, RRsets, тип, TTL и разрешённые значения | Собственные Zone/RecordSet карточки; A/AAAA связать с известным IP, CNAME как DNS-ссылку, не как физическое соединение |
| S3 | Бакет, проект/регион, настройки доступа, versioning, lifecycle, домены, доступная статистика | Карточка бакета; связи с доменами и документированными private endpoints. Размер может быть недоступен или запаздывать |
| Managed Kubernetes | Cluster/nodegroup/node IDs, версии, размещение, конфигурация, endpoint и сети | Карточка управляемого кластера; ссылки на облачные VM по явным ID. Не считать Kubernetes cluster кластером гипервизоров |
| Managed DB | Cluster ID, движок/версия, topology, размеры, адреса, сети, параметры бэкапов | Карточка сервиса; не создавать фиктивную VM по адресу БД |
| Load balancer | VIP, listeners, pools, members, health configuration | Карточка сервиса и связи с IP/backend по явным данным; не выдавать балансировку за кабель |
| Global Router | Router, подключённые сети, подсети, маршруты | Карточка маршрутизатора провайдера и связи сетевых областей; без выдуманных физических интерфейсов |
| Остальные продукты | ID, тип, размещение, безопасная конфигурация и зависимости | Отдельный адаптер и карточки того же реестра; никаких автоматических совпадений по названию |

DNS-зона не доказывает регистрацию домена у Selectel. Домены бакетов, DNS-зоны,
RRsets и регистрационные сведения различать. Совпадение DNS/IP даёт связь адресации,
но не доказательство владельца сервера или размещения workload.

## Общий механизм

1. **Подключение.** Проверить аккаунт, хранить ссылку на защищённые credentials.
   Для постоянной работы получать и обновлять account/project IAM-токены сервисного
   пользователя автоматически. Права чтения проверять отдельно по продуктам.
2. **Обнаружение.** Перечислять проекты и области; сочетать catalog endpoints с
   явными документированными API продуктов. Сам каталог не перечисляет все покупки.
3. **Сбор.** Адаптер объявляет версию, продукты/виды ресурсов, scope, разрешённые
   поля, пагинацию, права, лимиты, ошибки и отношения. Ошибка одного проекта не
   уничтожает данные другого. Секреты не проходят в журналы и снимки.
4. **Реестр.** Отдельно сохранять identity, безопасные свойства, observed_at,
   last_success_at, доступность секций, версию адаптера и provenance отношений.
   Уникальный ключ использует provider/account/service/kind/native ID и области,
   в которых API гарантирует уникальность. Регион/AZ не всегда часть identity:
   перемещение того же ресурса не должно создавать дубликат. Существующие ключи
   Guard сохранять; изменения формата — только совместимой миграцией.
5. **Сопоставление.** Сначала существующий binding, затем подтверждённые нативные
   ID и однозначные связи API. Имя, публичный IP, общий VLAN и Site — кандидаты,
   не достаточное основание присвоить объект. Частные IP сравнивать в сетевой области.
6. **План и применение.** Отдельно планировать создание, обновление и конфликты.
   Новые объекты разрешать автоматической политикой только при полной необходимой
   идентичности, корректном размещении и отсутствии конфликтующих кандидатов.
   Иначе сохранять ресурс в реестре для разбора, не создавать второй Device/VM.
   Guard проверяет права полей, версии и идемпотентность непосредственно при записи.
7. **Отображение.** Карточка аккаунта → проекты/регионы → ресурсы/связи. На объекте
   показать что известно, источник, давность и причину пробела. Map получает те же
   типизированные отношения: размещение, выделение, назначение, логический путь,
   физическая связь. Отсутствие одной связи не скрывает подтверждённые участки.

Повторный запуск без изменений должен давать пустой план. Порядок подключения
Selectel и гипервизора не меняет идентичность существующего объекта. Не переносить
IP гостя на хост, не заменять management IP и не переписывать NAT-ссылки.

Selectel отвечает за подтверждённые provider-поля и выделенные ресурсы. Гипервизор
отвечает за наблюдаемую конфигурацию хоста/гостей. Приоритет Selectel не означает
приоритет для всех полей Device. Административное состояние порта, carrier и
фактическая физическая связь — разные сведения.

## Полнота и исчезновение ресурсов

Отдельно показывать: прочитано, успешно пусто, частичный сбор, отказ доступа,
недоступный API, неподдерживаемый тип, исключено настройкой, устаревший снимок.
HTTP 200 с пустым списком подтверждает только видимость в данной области;
403, отсутствие endpoint и неподдержанный адаптер не означают отсутствие ресурсов.
При отсутствии адаптера продукт не должен выглядеть успешно синхронизированным.

Не удалять объект при неудачном или неполном сборе. При исчезновении после полного
сбора области сначала отмечать missing с временем и сохранять историю; retirement
должен иметь отдельную политику. Потеря доступа к проекту не равна удалению проекта.
Потеря Selectel-связи не разрешает удаление гостевых VM, управляемых гипервизором.

## Порядок реализации и приёмка

1. Единый реестр возможностей и отчёт аккаунта: для каждого продукта видно,
   реализован ли сбор, проверен ли доступ, что получено и чего не хватает.
   Это первый следующий исполняемый результат; повторный server-only импорт
   не заменяет этот этап.
2. Поддерживаемые сейчас ресурсы довести до полного контракта: dedicated/cloud,
   сети и диски, DNS RRsets, S3 metadata. Реальные ответы сверять на тестовом,
   fixtures очищать от идентификаторов внутренней инфраструктуры и секретов.
3. Добавить адаптеры Kubernetes и Managed DB, даже если текущий аккаунт пуст:
   проверять пустую область, отказ доступа и синтетические примеры документированной
   схемы. До испытания на реальных ресурсах отмечать ограничение проверки.
4. Native-проекция и безопасное автоматическое создание: проверить независимый
   dedicated без гипервизора, VM вне ESXi/Proxmox, пересекающиеся private IP,
   multiattach, одинаковые имена, повторный сбор, смену размещения и потери доступа.
5. Постоянное подключение, расписание, обновление токенов, изоляция аккаунтов,
   concurrency/retries и восстановление после перезапуска; затем общий UI/Map.

Для каждой поставки: перечень действительно поддерживаемых сущностей, тесты
пагинации/частичных ответов/ошибок доступа, отсутствие секретов, проверка Guard,
пустой повторный план и сохранность существующих назначений/истории. Тестовые ID
допустимы в acceptance-командах, но не в алгоритмах сопоставления.
