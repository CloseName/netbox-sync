# Дополнительные сведения о физических портах Selectel

Этап: исследование API на тестовом стенде, 2026-10-13. Это отдельный сбор
свидетельств для общего алгоритма, ещё не автоматическое создание кабелей.

## Что проверяем

Официальная [спецификация Dedicated API](https://docs.selectel.ru/api/dedicated/)
описывает методы ниже. Используется базовый URL
`https://api.selectel.ru/servers/v2`, как в
[официальном SDK](https://github.com/selectel/dedicated-go).

| GET относительно базового URL | Назначение |
|---|---|
| `/resource` и `/resource/{uuid}` | Ресурс, область размещения и hardware UUID |
| `/resource/{uuid}/aux_network_info` | Дополнительные сведения о портах ресурса |
| `/network/port/hw/{hw_uuid}` | Порты конкретного оборудования |
| `/network/port/{uuid}` | Идентичность и состояние порта, признаки агрегации |
| `/network/port/{uuid}/network` | Сети, подключённые к порту |

В схеме `aux_network_info` есть `mac_address`, `peer_name`, `peer_ip`, ASN,
`client_ip`, `subnet`, `availability_zone`, `leaf_pairs`, `loopback_ips` и
`network_interfaces_ip`. Их наличие в схеме не гарантирует заполнение для
конкретного типа сервера. Роль MAC (NIC сервера или оборудование сети) пока
не подтверждена. Эти значения нельзя сразу применять как доказательство кабеля.

## Сбор без изменения конфигурации

`python -m selectel_audit.port_probe --account ACCOUNT --output DIR` запрашивает
IAM-токен скрытым вводом, проверяет область аккаунта и автоматически обходит
видимые выделенные ресурсы. Идентификаторы серверов, NIC и NetBox не зашиты.
Токен не передаётся через аргументы командной строки и не сохраняется в отчётах.
Остаются только разрешённые технические поля; свободный текст и секреты исключены.

`deploy/probe-selectel-ports-test.sh ACCOUNT` запускает сбор в изолированном
контейнере на `netbox-test`. Образ должен быть предварительно собран из той же
ревизии. Скрипт не импортирует результаты, не обновляет Guard/Sync и не обращается
к NetBox. Существующие IP управления и назначения гостям сохраняются.

Файлы: `summary.json` — краткий итог и найденные дополнительные сведения;
`ports.json` — выбранные технические поля по каждому endpoint с временем запроса.
Это не полный дамп ответов API. Для каждого запроса сохраняется отдельный статус:
получено, пусто, 403, 404, 202, ошибка или неполная пагинация. HTTP 404 не трактуется
как доказательство отсутствия услуги, HTTP 200 — как полнота аккаунта. 202 не
вызывает запуск фоновых действий или бесконечный опрос. Ограничения числа запросов,
ресурсов и портов отмечаются явно. Сбор сохраняет частичный отчёт при отказах.

## Условия будущего автоматического сопоставления

### Уточнение диагностики (probe_version 2)

Режим `--profile auxiliary` читает текущий список ресурсов аккаунта и только
`/resource/{uuid}/aux_network_info` для каждого подходящего ресурса. Запуск:
`bash deploy/probe-selectel-ports-test.sh ACCOUNT auxiliary`.
Полный режим остаётся доступен по умолчанию. Повторный сбор не использует
жёстко заданные UUID и не требует ранее сохранённого отчёта.

Отдельно фиксируются отсутствующий/null `result`, отсутствующий/null `ports`,
пустой список, неожиданный тип и неверный тип элемента списка. `not_reported`
означает отсутствие поля/значения в ответе, а не отсутствие услуги, прав или
физического соединения. Неизвестный формат остаётся `unavailable`.
В `diagnostics` сохраняются типы известных полей, число неизвестных полей и
тип/размер списка. Неизвестные имена ключей и произвольные значения не сохраняются.
Старые отчёты восстановить до исходной структуры нельзя: нужен новый GET.

### Вопросы для поддержки Selectel — черновик, не отправлен

1. Для каких типов выделенных серверов заполняется `aux_network_info`?
   Может ли успешный ответ содержать null `uuid`, `location_uuid`, `state` и
   отсутствующий либо null `ports`? Как отличить отсутствие данных от ограничения
   доступа, какие минимальные IAM-разрешения нужны?
2. Что именно означает `mac_address` внутри дополнительных сведений порта:
   постоянный MAC NIC сервера, MAC оборудования провайдера или иное значение?
3. Есть ли поддерживаемый API чтения соответствия resource UUID → hardware UUID →
   port UUID → физический NIC сервера, включая MAC, PCI/номер NIC и агрегацию?
4. Доступны ли chassis/switch ID и физический port ID, а также LLDP/CDP или таблица
   изученных MAC? Если доступна таблица MAC, как отличить NIC от MAC гостевых VM?
5. Какие поля показывают административное включение, фактический carrier и
   намеренное неиспользование? Как трактовать `speed=AUTO`?

В просмотренной публичной спецификации Dedicated API отдельного метода LLDP/CDP
не найдено. Это не доказывает отсутствие такой возможности у Selectel. Ответ
поддержки нужен для общего контракта, а не для ручной привязки двух серверов.

### Правила сопоставления

- Сохранить отдельно постоянный provider UUID, связь с hardware UUID, сетевую
  область и наблюдения гипервизора. Имя порта без идентичности коммутатора
  не уникально; одинаковый `GE1/0/4` не означает один порт.
- Подтверждать pNIC по проверенной семантике данных: например, документированному
  MAC серверного интерфейса и уникальному совпадению в актуальном снимке хоста,
  либо согласованным идентификаторам chassis/port в API и LLDP/CDP. При противоречии
  или неоднозначности оставлять связь неподтверждённой с объяснением причины.
- `is_enabled` — состояние из API, а не доказательство доступности, трафика или
  намерения владельца. Не включать отключённые порты и не удалять существующие
  связи из-за отключения. Агрегированные порты не сводить к одному NIC.
- Путь VM → bridge/vSwitch → pNIC полезен независимо от подтверждения порта
  провайдера. Различать конфигурационный путь, наблюдение соседства и кабель.
- Схемы draw.io и ручные таблицы — дополнительный источник с происхождением
  и датой; не источник автоматической записи. Цвета и отсутствие линии не
  доказывают отключение порта. Расхождения показывать пользователю.
- Не устанавливать LLDP-службы, не менять ACL и сетевые настройки автоматически.
  При подключении объяснять недостающую возможность и её минимальные требования.

После получения реальных ответов уточняется контракт полей и добавляется
автоматический сбор в обычный цикл. Сам probe не доказывает готовность такого
сопоставления. Общие требования: [автоматизация сети](provider-network-automation.md).


## Ответ поддержки, переданный пользователем 2026-10-14

Источник: текст обращения и ответ Selectel в переписке проекта. Номер тикета
и точная версия API не предоставлены. Ниже сохранены сведения поддержки,
а не результаты нашей проверки методов.

Исходное наблюдение для аккаунта 29916: для всех 25 серверов
`GET /servers/v2/resource/{uuid}/aux_network_info` вернул `status: success`
и заполненный `task_id`, но поля `result`, включая `ports`, были `null`.
Через `/network/port/hw/{hw_uuid}` и `/network/port/{uuid}` обнаружены 48 портов;
`aux_network_info.mac_address`, `peer_name`, `peer_ip` также пустые.

Поддержка сообщила:

- Операция `aux_network_info` асинхронная и поддерживается для выделенных серверов.
- Результат получают отдельно по `task_id` либо через основной метод в зависимости
  от версии API. `status: success` в описанном ответе, по словам поддержки,
  не означает, что сами данные уже представлены в `result`.
- Возможные пути: `GET /servers/v2/task/{task_id}` либо
  `GET /servers/v2/resource/{uuid}/aux_network_info/{task_id}`.
  В ответе использованы слова «обычно» и «в некоторых версиях»: ни один из этих
  путей пока не подтверждён для нашего аккаунта. Не добавлять автоматический
  перебор предполагаемых endpoint в production-сборщик.
- Требуются права чтения выделенных серверов в соответствующей области;
  поддержка привела обозначение `server:read`. Точное имя роли и область
  назначения требуют подтверждения, это не проверенная инструкция IAM.

Открытые вопросы из обращения, на которые ответа пока нет:

1. Чей MAC обозначает `aux_network_info.mac_address`: NIC сервера или сетевого
   оборудования провайдера?
2. Есть ли общий API соответствия UUID порта физическому NIC по постоянному MAC,
   номеру NIC либо иному устойчивому идентификатору?

Следующий этап: запросить у поддержки точный endpoint/версию, пример обезличенного
ответа, статусы готовности, срок хранения результата и правила повторного опроса.
Затем проверить чтение конкретного полученного `task_id` на тестовом стенде,
с ограничением времени/числа запросов и без изменения конфигурации серверов.
Пустой ответ остаётся «сведения не получены», а не «портов нет».
Даже заполненный MAC не использовать для привязок, пока не установлена его роль.
Сохранение этой заметки не меняет production, IP, pfSense или существующие связи.
