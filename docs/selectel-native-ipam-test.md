# Native IPAM для двух принятых серверов Selectel

Работает с NetBox 4.7.0 и сохранённым ProviderInventory. IAM-токен не нужен.
Deployment script допускает только root на netbox-test, compose /netbox-test,
аккаунт 29916, Device 28/29 и заранее принятые UUID ресурсов. Production не трогает.

## Объекты и отношения

- IPAddress: фактический адрес с сообщённой Selectel маской. Уже назначенные
  адреса сохраняют интерфейс и primary-ссылки. Новые адреса остаются неназначенными.
- Prefix: именно выделенный блок. Поэтому 5.188.156.24/32 становится Prefix,
  а сообщённая маска 255.255.255.0 даёт IPAddress 5.188.156.24/24. Это не выделение
  клиенту всего /24 и не утверждение о конфигурации интерфейса.
- VLANGroup: account + location UUID + network_type. Публичный и локальный VLAN
  1608 — разные услуги, не объединяются. VLAN связан с отдельным network UUID.
- Prefix.vlan заполняется только по подтверждённому network UUID. При отсутствии
  сети в каталоге сохраняется allocation, выводится NETWORK_NOT_REPORTED,
  VLAN по числовой строке из IP не угадывается (в старой выгрузке это сеть 106).
- ProviderNetworkLink: allocation IP → выделенный сервер; subnet → сервер;
  attachment VLAN → сервер с именами портов **провайдера**. Это не Cable и не
  соответствие имени provider port имени eno/vmnic. NAT и маршруты не создаются.

Уже существующие глобальные IP переиспользуются при однозначном адресе/маске и
назначении самому хосту либо VM с device_id этого хоста. IP в других VRF остаются
отдельными. Частные сети не проецируются без явно подтверждённого routing context.
Существующий Prefix переиспользуется при однозначном CIDR/VRF и совместимом VLAN;
пустой VLAN может быть заполнен по UUID из review. Остальные поля сохраняются.

ProviderIPAMObject хранит постоянное соответствие UUID → native ID и claims:
IP address/VRF, Prefix CIDR/VRF/VLAN/scope, VLAN VID/group/site, VLANGroup slug/scope.
SQL-триггеры блокируют изменение этих полей, удаление и дублирование принятого
глобального IP/Prefix. Неуправляемые поля и реальные назначения интерфейсам могут
обновляться обычными источниками. Имя/описание существующего объекта не заменяются.

Accepted mapping/link/receipt неизменяемы. Если identity, маска, routing context
или принятое доказательство связи изменились, команда отказывает и требует
отдельного reconciliation; автоматическое освобождение адресов не реализовано.
Пропавшие старые связи сохраняются и перечисляются в retained_links. Snapshot с
неуспешным/retained сетевым разделом не используется для новых записей. Возраст
снимка выводится в review; свежесть относительно Selectel без нового опроса
подтвердить нельзя. Повторный импорт данных и native projection — отдельные шаги.

## Применение

1. Checkout закреплённого SHA; `bash deploy/update-selectel-test.sh` устанавливает
   Guard и миграцию 0009, проверяет четыре SQL-триггера и обе ревизии образов.
2. `bash deploy/project-selectel-ipam-test.sh` готовит `/var/tmp/selectel-ipam.*/review.json`
   и `apply.sh`. В плане — native IDs, действия, исходные значения, UUID, снимок,
   назначения и изменения Prefix.vlan. Credentials в файлах отсутствуют.
3. Исполнить напечатанный `bash .../apply.sh`. Повторно проверяется fingerprint;
   при изменении NetBox/реестра нужен новый review. Применение атомарно, журнал
   Guard сохраняет before/evidence/результат. Затем проверяется нулевой повторный план.

Для уже согласованного применения к этим двум серверам можно выполнить
`bash deploy/project-selectel-ipam-test.sh --apply`: план сохраняется и печатается,
затем исполняется тот же `apply.sh`. Без флага выполняется только preview.

На время короткой транзакции блокируются записи в затрагиваемые таблицы;
ожидание блокировки ограничено 10 секундами. Под блокировкой нет запросов Selectel.
Планирование только читает. Ошибка любого объекта откатывает весь пакет.

## Отображение / Map

В native IPAM работают стандартные поиск и карточки адресов, Prefix и VLAN.
На Device/IPAddress/Prefix/VLAN добавляется таблица «Selectel · сети провайдера»
со ссылками на native объекты, сервер, VLAN/Prefix и фактический интерфейс.
Старые Custom Fields пока сохранены для совместимости; это не полный редизайн.

GET `/api/plugins/netbox-sync-guard/providers/networks/v1/<kind>/<id>/`,
kind=device|ipaddress|prefix|vlan, schema=netbox-sync.provider-network.v1.
API и HTML используют одинаковую фильтрацию объектных view permissions,
включая родительскую VM/Device и интерфейс фактического назначения.

Приёмка: management 92.53.72.222 и 10.24.0.2 сохранены; .249 остаётся на гостевой
pfSense; .246 и .24 не получают выдуманный интерфейс; общий /28 создан один раз;
повторный план 0; ESXi/PVE sync после применения не вызывает циклических изменений.

## Пути по конфигурации гипервизора

В следующем этапе `proxmox_host_network` автоматически создаётся Guard как скрытое
JSON-поле и наполняется обычной синхронизацией Proxmox. В Device это отдельная
таблица «Сеть хоста Proxmox», а не сырой JSON. Уже собираемый ESXi snapshot используется
для путей VMkernel / port group / standard vSwitch / pNIC.

Для IP с подтверждённым назначением новая секция показывает конфигурационный путь:
для host interface — от него; для VM interface — от source_bridge, только при совпадении
источника с хостом и VM.device. Linux bridge, bond и явный VLAN parent поддерживаются.
Все участники bond отображаются как возможные ветви, не как активный маршрут трафика.
DVS, OVS, SDN, отсутствующие parents, дубли и циклы не достраиваются предположениями.

API Proxmox возвращает bond members в `slaves`. Признак общей ожидающей конфигурации
передаётся метаданными ответа `changes`, которые обычный proxmoxer GET не возвращает
в списке data. Поэтому отсутствие pending в строке означает «неизвестно», а не
«всё применено». Документация/исходник:
https://github.com/proxmox/pve-manager/blob/master/PVE/API2/Network.pm

Путь не доказывает физическое соединение с портом Selectel, разрешение VLAN на всех
участках, NAT или текущую доступность. ProviderNetworkLink остаётся неизменным.
Для подтверждения внешнего ребра нужны сведения о соседнем коммутаторе и порте
(например CDP/LLDP с обеими идентичностями) либо подтверждённая провайдером связь
с MAC физического адаптера. Один номер ge-1/0/4 или VLAN 1608 недостаточен.

Порядок тестового обновления: Guard → тестовый NetBox Sync → применённый сбор двух
источников → read-only проверка. Обновление общего production collector в этот этап
не входит. На старом collector у Proxmox честно будет отсутствовать snapshot;
ESXi путь из уже сохранённого snapshot доступен после обновления Guard.
