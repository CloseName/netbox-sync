# Веб-настройка источников: решение по авторизации и политике

Статус: **предложение для архитектурного решения, не реализация и не разрешение на расширение доступа**. База ревью: c1e8b1d. UI-исправления и доказательства: 9a0ba95, [отчёт](ux-hardening-review.md). Этот документ не вводит вход, пользователей, endpoint управления политикой или новые разрешённые назначения.

## Исходный контракт и проблема

В api/app.py сейчас есть точный Host/Origin, CSRF-маркер и ограничение по состоянию Bootstrap, но нет аутентифицированного пользователя и серверных пользовательских permissions. READY означает готовность NetBox, а не полномочия человека. Адрес, пришедший из браузера, также не является идентичностью. Поэтому нельзя открывать чтение внутренней сетевой политики или её изменение только потому, что браузер прошёл Origin/CSRF.

api/settings.py считывает NETBOX_SYNC_ONBOARDING_ALLOWED_CIDRS, DENIED_CIDRS, ALLOWED_HOSTS, ALLOWED_SUFFIXES (все с префиксом NETBOX_SYNC_ONBOARDING_). api/egress.py применяет deny-wins; при отсутствии явных allow разрешены RFC1918, публичным назначениям нужен opt-in. Это **политика подключения при регистрации**, не общий сетевой firewall для всех последующих Discovery/Plan/Apply. Публичное изменение этой политики нельзя незаметно выдавать за управление всем egress.

Probe выполняется отдельным ограниченным компонентом, проверяет все DNS-ответы и фиксирует выбранный IPv4 на соединение, сохраняя TLS hostname. Broker остаётся network_mode: none. API не получает provider egress, DB writer privileges или доступ к Docker/systemd. Эти границы обязательны и для следующего этапа.

## Рекомендуемое решение и альтернативы

Предлагается сначала минимальная серверная авторизация с реальными principals, сессиями и permissions, затем веб-политика. Минимальная означает одну доступную роль администратора, а не отсутствие контроля на остальных API.

| Вариант | Что даёт | Цена и ограничения |
|---|---|---|
| Минимальная авторизация, локальный первый администратор | Работает без IdP; закрывает анонимное управление и даёт actor для аудита; небольшой permission-контракт можно расширить | Нужно безопасно реализовать хранение пароля, сессии, rate limits, восстановление доступа. Пока все допущенные пользователи администраторы, нет делегирования |
| Сразу полноценный RBAC + корпоративный IdP | Разделение admin/operator/viewer, группы, централизованный отзыв и MFA | Нужны решения по IdP, группам, source scopes, service accounts, миграции прав и восстановлению; существенно больше матрица проверок и срок до веб-настройки |
| Только идентичность внешнего ingress | Может использовать существующий корпоративный вход | Произвольный X-User не доверен. Нужен отдельный проверенный протокол assertions, bounded ingress trust, защита прямого upstream, отзыв и отказ при отсутствии identity. Не универсальный default для двух режимов deployment |

Рекомендация к принятию: локальный первый администратор + непрозрачные серверные сессии как автономный минимальный этап. Если уже выбран корпоративный OIDC IdP, до реализации заменить способ входа на OIDC, сохранив principal/permission/policy контракт ниже. Не реализовывать две системы входа одновременно без необходимости. Выбор локального входа требует отдельного утверждения; этот review не делает его за оператора.

## Серверная идентичность и первое получение доступа

Principal — UUID, присвоенный сервером, с active/disabled, auth_version и привязками identity. Логин и отображаемое имя не используются как ключ полномочий. При локальном входе хранится только устойчивый password hash (предлагается Argon2id с параметрами по актуальным рекомендациям и измеренному ресурсу). Не журналировать пароль; ограничивать частоту попыток, иметь idle/absolute TTL и серверный отзыв сессий. Не вводить общий admin token в frontend/env.

Первое зачисление администратора — явная root-only host-команда нового этапа авторизации. Она выдаёт одноразовое случайное приглашение с коротким TTL в файл 0600 либо защищённый терминальный вывод по запросу оператора; не в argv, env или журналы службы. В хранилище остаётся hash приглашения. Оператор открывает HTTPS enrollment-форму, вводит приглашение через POST и задаёт свои данные. Атомарное потребление приглашения и создание первого principal в одной транзакции; конкурирующий запрос не создаёт второго первого администратора. Знание URL, первый визит или завершённый Bootstrap не предоставляют права. В браузере token не помещается в URL/history.

До enrollment UI показывает необходимость обращения к оператору, все бизнес-API требуют авторизации. На существующей установке upgrade не присваивает владельца анонимному браузеру; host preflight требует явный план enrollment до активации режима. Фоновые scheduler/worker продолжают свой отдельный machine-контракт, не используют cookie браузера. Аварийное восстановление — root-only audited команда, новый одноразовый enrollment и отзыв сессий затронутого principal; не скрытый HTTP bypass.

Сессия — случайный opaque handle; сервер хранит hash, principal, TTL, auth_version. Cookie __Host-netbox-sync-session: Secure, HttpOnly, SameSite=Lax, Path=/, без Domain. Ротация при входе/повышении прав, удаление при logout, смене пароля и блокировке пользователя. Origin/CSRF остаются дополнительными проверками записи. Ошибки входа не раскрывают существование пользователя. Секреты enrollment/сессии и поля пароля исключены из audit/request logs.

## Permissions и процессная граница

Предлагаемые стабильные permissions: policy.read, policy.write, source.read, source.probe, source.register, source.configure, source.schedule, source.plan, source.apply, source.remove, run.read, diagnostics.read, bootstrap.manage, identity.manage. Этот список нужно сверить с полной таблицей существующих API до реализации; новое действие по умолчанию запрещено.

Для policy GET требуется policy.read; для изменения policy.write, активная сессия и недавнее подтверждение входа. Для запуска probe нужны source.probe и разрешённое назначение; для регистрации — source.register и актуальное свидетельство проверки. Отмена onboarding проверяется по владельцу. /me может вернуть UI capabilities, но кнопки не заменяют серверную проверку. Неаутентифицированный запрос — 401; недостаточные права — 403; недоступный сервис авторизации — отказ, не fallback к anonymous.

Сервер проверяет каждую операцию, включая старые маршруты и прямой upstream. Нельзя защитить только редактор policy, оставив анонимный probe или source registration. Health/liveness могут иметь отдельный минимальный публичный ответ без конфигурации, identity, адресов и секретов.

Рекомендуем отдельный auth/policy control worker на приватной DB-сети, Unix interface и узкий протокол вместо передачи произвольного SQL. API получает проверенный request principal, но не DB writer к таблицам auth/policy. Worker проверяет сессию и permission сам при изменении; нельзя доверять переданному API полю role. RPC peer UID защищает вход между процессами; пользовательская сессия защищает действие человека. Broker остаётся только секретным filesystem-компонентом без сети. Новый worker не имеет provider credentials, NetBox token, Docker socket, systemd или provider egress. Это предлагаемая новая граница, требующая отдельного ревью, а не расширение lifecycle-worker на все административные задачи.

## Хранение и применение без перезапуска

Предлагаемые отдельные таблицы: principals/identity_bindings/sessions, policy_revisions, active_policy, policy_audit. Migration-owner создаёт их; auth/policy worker имеет только необходимые права на эти таблицы. Runtime/discovery/apply/API роли не получают общий writer. Внешний и bundled PostgreSQL используют одинаковый контракт grants.

Изменение: сервер валидирует канонический документ, требует expected_revision и idempotency key, в транзакции записывает неизменяемую ревизию, аудит и переключает active_policy. Конкурирующая ревизия — 409 с требованием пересмотра, не перетирание. Audit: actor UUID, время сервера, request ID, основание, безопасный diff, исходная/новая revision, результат; без паролей, token, cookie или ответов provider. Просмотр аудита также защищён. Требуется политика срока хранения; revision history не даёт права автоматически откатить чужое изменение.

Перед каждым новым probe читается актуальная разрешённая ревизия. Нет бессрочного process cache; недоступная политика останавливает новый запрос. Worker проверяет revision перед сетевым подключением, не доверяет произвольной policy из браузера. Регистрационное свидетельство привязано к principal, провайдеру, назначению, revision и сроку; после изменения revision требуется новый probe. Прошедшая регистрацию конфигурация не меняется молча из-за новой политики.

Линеаризационная точка — разрешение нового соединения по актуальной revision. Уже начатый ограниченный по времени probe может завершиться; изменение policy не заявляется принудительным разрывом TCP. Pending/queued запрос при устаревшей revision повторно валидируется до connect. Это отдельный policy fence; shared apply lock и digest/revision fencing существующих sync/lifecycle операций не заменяются и не ослабляются.

Backup включает таблицы policy, audit, identities с минимальными grants backup-role; runtime snapshots, credentials и onboarding сохраняются штатно. Restore должен инвалидировать сессии и enrollment tokens, сохранить audit/политику и заново проверить host ceiling. Нельзя переносом backup расширить target-ограничения или восстановить действующие сессии старого сервера. Это новые acceptance-тесты будущей реализации.

## Совместимость с env и стандартный public-source flow

До явного перехода — режим legacy-env с прежней семантикой; обновление само по себе не расширяет сеть. UI показывает, что правило ограничено host policy, и не обещает обойти его.

Для нового режима предлагается разделить неизменяемые защитные запреты, операторский ceiling и DB allow/deny. Deny всегда имеет приоритет. Существующие ALLOWED_* при наличии становятся потолком: UI может сузить его, но не расширить. DENIED_CIDRS сохраняются. Пустые allow в legacy-env по-прежнему означают только RFC1918, а не все публичные адреса. Действующие localhost/link-local/metadata/служебные назначения и порты не разблокируются пользовательской policy.

При единовременном явном переходе оператор через поддерживаемую host-команду или installer option выбирает managed policy ceiling: public/private IPv4 для фиксированных Proxmox/ESXi портов либо более узкие корпоративные пределы. Команда валидирует текущий env-контракт, импортирует baseline и аудит, явно показывает расширение относительно RFC1918. Предлагаемые команды ещё не существуют; документ не является runbook для их запуска. Для строгого existing ceiling публичное исключение за его пределами требует host-admin, и это осознанное ограничение. Новые установки выбирают managed ceiling явно, после настройки admin; до этого public не открыт.

Обычный сценарий **после принятия managed ceiling**: администратор входит → Add source → вводит DNS-имя публичного источника → видит безопасное объяснение запрета → открывает встроенное добавление точного hostname, видит effective policy/порты и подтверждает → сервер проверяет policy.write и атомарно создаёт правило → выполняется TLS-проверенный probe → review → source.register с авто-sync OFF. Credentials не теряются из-за раскрытия справки, но не хранятся в policy/audit. Другой пользователь без policy.write получает запрос к администратору, не кнопку обхода. На каждый источник файлы не редактируются и службы не перезапускаются.

Не разрешать произвольный URL, порт, redirect или proxy из браузера. Проверять все DNS-ответы и pin соединение; TTL/смена revision не дают использовать старый результат. IPv6 не объявлять поддержанным исходящим транспортом без отдельной реализации/тестов. Нужно явно перечислить защищённые endpoint приложения (DB, NetBox, ingress, workers) и протестировать обходы через DNS/IP; имя само по себе не доказывает изоляцию. Более широкая политика для текущих scheduled Discovery/Apply — отдельное решение, не скрытый побочный эффект onboarding.

## RBAC и LDAPS после минимального этапа

Рекомендуемая следующая матрица: admin управляет identities и policy; operator читает разрешённые sources и выполняет отдельно назначенные probe/register/plan/apply/schedule действия; viewer только читает разрешённую область. Remove Source и управление credentials не выдавать автоматически любому operator. policy.read и diagnostics.read могут раскрывать внутренние адреса: viewer не получает их по имени роли без решения. Source scope проверяется на сервере на чтение, действие и retained Run History; глобальные aggregates не должны раскрывать чужие источники.

OIDC binding — (issuer, sub), не email/display name. Для LDAPS предпочтителен корпоративный IdP bridge: приложение не обрабатывает AD password. Если требуется прямой LDAPS, нужны отдельный узкий auth connector, проверка CA/hostname, fail closed, bounded LDAP egress, read-only bind account и защищённый secret, ограничения query/groups и сроки отзыва. Ни API, ни broker не подключаются к LDAP ради удобства. Mapping групп на роли явный, по стабильным идентификаторам; новая группа или совпавшее имя не создаёт admin. Отзыв учитывается сервером с ограниченной задержкой, уже выпущенная сессия не вечное разрешение.

## Порядок и критерии принятия

1. Утвердить способ входа, первичное enrollment/recovery, полный реестр permissions и процессную границу. Реализовать сессии и deny-by-default на всех бизнес-маршрутах; пока только admin, без UI policy.
2. Реализовать policy store/worker, revision fences, import/ceiling, аудит и встроенный public-source flow. Только после пункта 1 открыть защищённые policy endpoints.
3. Добавить admin/operator/viewer + source scopes; затем корпоративные bindings. Если IdP уже обязателен, его auth adapter входит в пункт 1, но не отменяет серверных permissions.

Минимальные acceptance: direct API без session; viewer/чужой source; Origin-correct, но неавторизованный POST; session revoke/expiry; двойное enrollment; конкурентные policy writers; stale probe receipt; смена DNS; недоступный auth worker; env ceiling и deny; backup/restore с инвалидированными сессиями; совместимость standalone/external ingress; broker network_mode:none; отсутствие API/DB host ports; отсутствие секретов в argv/env/logs/audit. Ни успешный GET версии, ни UI fixture не заменяют production Compose transport/discovery проверку.

**Решение к принятию:** согласовать минимальную локальную авторизацию (или указать готовый OIDC IdP), отдельный auth/policy worker и явный managed ceiling. Полноценный RBAC не нужен для первого безопасного admin-only public-source flow, но модель principals/permissions и закрытие всех API нужны сразу.

## Основания

[OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html): отказ по умолчанию, проверка полномочий на каждом запросе, тестирование границ доступа.
[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html): защита cookie, жизненный цикл/ротация сессии.
[NIST SP 800-63B Session Management](https://pages.nist.gov/800-63-4/sp800-63b/session/): серверное управление сессией и ограничение срока, cookie-защита.
Это ориентиры проектирования, не заявление сертификации. Точные параметры hash/TTL/MFA подлежат отдельному security review перед реализацией.
