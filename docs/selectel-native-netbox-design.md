# Selectel: штатные объекты NetBox и связи для Map

Дата: 2026-10-12. Статус: первый этап native IPAM реализован в тестовой ветке;
применение на сервере выполняется отдельно через review/apply.
Основание: пользователь подтвердил импорт 68 серверов и запросил полноценную
структуру NetBox вместо представления конфигурации в Custom Fields.
Production не изменять; реализация и приёмка сначала на тестовой установке.

## Подтверждённое текущее состояние

- Импорт аккаунта 29916: 68 записей реестра, Device 28/29 обновлены до revision 2.
- Остальные 66 ресурсов ещё не имеют принятой связи с native Device/VM.
- Guard защищает провайдерские Custom Fields на Device/VM. Миграция 0009 добавляет
  защиту идентичности native IPAM и постоянных сетевых связей; перенос площадок
  и проекция модулей остаются отдельными этапами.
- Device остаётся основной карточкой физического хоста. Cluster — логическая
  группировка гипервизоров и VM; не объект владения физическими дисками.
- Последний пользовательский запрос расширяет направление учёта физических
  компонентов относительно прежнего REQ-008. Детализация компонентов ниже —
  предложение, а не утверждение о доступности слотов/серийников в Selectel API.

## Предлагаемое отображение в NetBox

| Сведения | Модель / место отображения | Условия |
| --- | --- | --- |
| Физическая площадка SPB-3 | Site `Selectel SPB-3`, при необходимости Site Group `Selectel` | По UUID площадки провайдера; не переносить все устройства старого Site `Selectel` |
| Помещение, ряд, стойка | Location, Rack | Только если API действительно сообщает эти сущности |
| Выделенный сервер | Существующий Device | Сохранённая provider binding, не повторное сопоставление по IP |
| Реальная ОС/гипервизор | Device.platform | Фактический опрос; шаблон установки провайдера не перезаписывает платформу |
| CPU/RAM/физические диски | Module, ModuleType/Profile, ModuleBay | Нужны достоверная идентичность/структура компонентов; не выдумывать физические слоты |
| Облачная VM | VirtualMachine с vCPUs/memory/platform | После разрешения идентичности; без фиктивного физического гипервизора Selectel |
| Диск VM | VirtualDisk | Только диск VM; отдельно проверить multiattach и shared volume |
| Сеть провайдера | VLAN/VLANGroup, Prefix, IPAddress | UUID сети, область L2/L3, маски и назначение; VID/CIDR не глобальная идентичность |
| Сетевой интерфейс | Device Interface / VMInterface, MACAddress | Подтверждённое соответствие, сохранение уже назначенных IP |
| Доступ Sync | Endpoint источника + проверенный management IP | Endpoint может включать DNS/порт/NAT; не тождественен выделенному провайдером IP |
| Принадлежность услуги и выделение адреса | ProviderBinding и типизированная связь провайдерского ресурса с native объектом | Не заменять Tenant/Owner смыслом «любой внешний поставщик» |

Для физических компонентов нельзя переводить агрегат `4 x 32 GB RAM` в четыре
якобы подтверждённых DIMM-слота. При отсутствии поштучной идентичности показывать
комплектацию и количество в компактном разделе «Оборудование» плагина. Modules
заполнять по подтверждённой компонентной инвентаризации. Групповые строки заказа
и реальные аппаратные компоненты должны различаться.

Шаблон `noos` не означает отсутствие работающей ОС; он не может заменить VMware
ESXi в platform. Образ установки `proxmox pve-9` не доказывает текущую версию 9.1.9.

## Два примера из имеющейся выгрузки

Device 28 ESXI-INFRA: существующий IP 92.53.72.222/29, ID 1738, назначен vmk0,
ID 21. При импорте Selectel использовать тот же IPAddress после проверки области,
не создавать вторую копию. Дополнительный 95.213.250.246/28 — выделен провайдером;
назначение его конкретному интерфейсу из этого факта не следует.

Device 29 NEW-INFRA-TEST: primary IP 10.24.0.2/24, ID 1712. Selectel выделил
95.213.250.249/28 и блок 5.188.156.24/32 (маска сети в API — /24).
В сохранённой выгрузке 95.213.250.249/28 уже
существует как IPAddress 1725 на VMInterface 3169 гостевой pfSense, VM 2609,
размещённой на Device 29. Сохранить это назначение; провайдерская принадлежность
связывается с IP, а не переносит IP на физический сервер. Для 5.188.156.24 точка
использования пока не подтверждена. Старые снимки — основание для плана, перед
apply нужно повторно проверить живые объекты.

У pfSense есть LAN 10.24.0.1/24. Это ещё не доказательство NAT/PAT между каждым
публичным адресом и 10.24.0.2. Нужны правила и маршруты. Не создавать NAT-связь
только потому, что firewall и хост размещены рядом.

## Сопоставление и конфликты

1. После принятия связи использовать provider UUID и сохранённую ссылку на объект.
2. IP — дополнительное наблюдение, не пожизненная идентичность сервера.
3. Искать существующий IPAddress в подтверждённом routing context; сравнивать
   host address и отдельно маску. Расхождение маски не исправлять без review.
4. Не создавать VRF автоматически на каждый аккаунт. VRF отражает независимую
   таблицу маршрутизации; принадлежность аккаунту/проекту хранится отдельно.
5. Не объединять сети по одному VLAN ID или одинаковому частному CIDR. При
   недостатке данных об области сохранять наблюдение и причину невозможности
   назначения. Подтверждённая общая сеть может использоваться несколькими хостами.
6. Не считать provider port с именем `ge-0/0/5` сетевым портом гипервизора.
   MAC, LLDP или иное явное соответствие требуется для физической связи.
7. Существующие неоднозначные объекты требуют разрешения конфликта; дальнейшие
   циклы по сохранённым связям автоматические. Полностью автоматический ввод
   не означает создание неподтверждённой топологии.

## Владельцы данных

Selectel отвечает за выделенный ресурс, физическое размещение, заказанную
комплектацию, выделение IP/подсетей и провайдерские сетевые отношения. ESXi/PVE
отвечают за фактические интерфейсы хоста, bridges/vSwitch, VLAN tagging, VM и
их размещение. pfSense — за фактические интерфейсы firewall, маршруты и правила.
Endpoint подключения — конфигурация источника Sync.

Guard должен закреплять владельца каждого native поля и отношения. При принятии
site Selectel старое значение source.site из Sync не должно возвращаться при
очередном опросе. План должен учитывать provider claims до записи, а SQL-защита
служит последним рубежом. Отсутствие новых данных не освобождает claim и не удаляет
объекты. Совместное изменение Device.site/Cluster.scope/VM.site допускается только
в согласованном плане с проверкой всех зависимостей; mixed-site cluster не
переносится целиком по одному серверу.

## Представление и API Map

Верх карточки Device: площадка, роль, platform, management IP, cluster — штатные
поля. В штатных разделах IPAM доступны поиск адреса/подсети и переход к реальному
интерфейсу. Отдельные компактные блоки Guard показывают услугу провайдера,
комплектацию с доступной детализацией и связанные сети со ссылками на native
объекты. Полный JSON остаётся техническим evidence; обычная карточка его не печатает.

Map читает native объекты и отношения Guard через версионированный API, не парсит
строки Custom Fields. Различать типы связей: размещение, членство в кластере,
назначение IP интерфейсу, выделение провайдером, L2 attachment, маршрут, NAT/PAT.
Для неподтверждённого сегмента показывать неизвестную связь. Обычный кабель или
непрерывный маршрут не рисовать вместо отсутствующего доказательства.

## Этапы и приёмка

1. Read-only план native проекции для Device 28/29 с существующими IDs, scope,
   before/after, доказательствами и конфликтами. Сначала IPAM и принадлежность
   адресов; затем согласованная миграция площадки и компонентов.
2. Типизированные связи провайдера и расширение Guard на native объекты/отношения.
   Проверки stale review, атомарного отката, replay, идемпотентности и конфликтов.
3. Дополнение Proxmox network collector связями bridge/bond/port/VLAN/MAC; перенос
   подтверждённых ESXi vmnic/vSwitch/portgroup/vmk отношений из снимков в общую модель.
4. Компактные блоки NetBox и API Map. Затем расширение с двух примеров на остальные
   ресурсы; отдельная приёмка перед production.

Критерии: поиск 95.213.250.249 открывает существующий IP на гостевой pfSense и
показывает Selectel allocation; primary Device 29 остаётся 10.24.0.2; 92.53.72.222
не дублируется; 5.188.156.24 виден как выделенный адрес с неизвестным фактическим
назначением; повторные Selectel и ESXi/PVE циклы не меняют владельческие поля по
кругу; одинаковые private CIDR в разных routing contexts не объединяются.
