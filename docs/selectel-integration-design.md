# Selectel: контракт будущей интеграции

Предложение для проверки по реальной выгрузке. Этот документ не утверждает, что
описанные UI, таблицы, custom fields и запись в NetBox уже реализованы. Первый
этап — [контейнер аудита](selectel-audit.md), работа только с тестовой установкой.

## Уточнение приоритетов и этапа — 12 октября 2026

После передачи двух успешных аудитов разработка продолжается от ff7e31e в ветке
Selectel. Исходные реальные JSON на этом рабочем месте не прочитаны; выводы ниже
основаны на передаче пользователя. Полнота аккаунтов не доказана: остаются пробелы
ports/subnets для трёх VM одного проекта, отсутствующий subnet у публичного порта
и расхождение Resell/Neutron floating IP. Это не блокирует модель и read-only UI,
но блокирует автоматическое применение соответствующих сетевых назначений.

Selectel — верхний уровень провайдерской принадлежности **после принятия связи**.
Это не разрешение переписывать весь объект по совпадению IP. Логическая иерархия:
провайдер → аккаунт → dedicated ресурс / Device → гипервизор / кластер → гостевые VM.
Для облака: провайдер → аккаунт → проект/регион → cloud VM. Наличие гипервизора
внутри облачной VM надо подтвердить отдельно. Физический хост публичного облака
не выдумывается. В стандартном NetBox нет универсального родителя «провайдер»
для кластеров: иерархия выводится по связям интеграции; Site остаётся размещением.

Порядок подключения не должен менять результат:
- ESXi/Proxmox первым: принять Selectel binding к существующему Device; ID, история,
  гостевые VM и hypervisor identities сохраняются.
- Selectel первым: после явного подтверждения регистрации гипервизора добавить
  hypervisor identity к тому же Device, а не создать второй. Guard проверяет обе
  связи. Имя/IP дают кандидата, но не разрешение присвоить существующий Device.
- Ресурс другого провайдера (включая Seam Networks) не относится к Selectel из-за
  Site с именем selectel. Отсутствие в Selectel тоже не доказывает другого провайдера.

### Поля и предотвращение перезаписи

Постоянные claims на поля хранить в модели интеграции/Guard: объект, поле,
владелец/connection, binding revision, основание, автор принятия. Они не равны
блокировке процесса и не управляются редактированием custom fields. Перед каждой
записью проверять claims; планирование ESXi/Proxmox и Selectel должно применять
одинаковую политику. Запретить обход со старого writer через Guard. При смене
claims между планом и apply план устаревает. Временный отказ API не снимает claims.

Selectel ведёт provider ID, подпись услуги, provider state и provider location.
Hypervisor ведёт техническую версию/состояние и своих гостей. Management IP и
имя существующего Device сохраняются; IP гостевого шлюза не переносится хосту.
Достоверные serial/model могут передаваться под управление Selectel отдельным
решением; hw_uuid и тариф такими полями не являются. Ручные поля не захватываются.

### Исправление Site

Сначала принять отображение Selectel location/AZ → NetBox Site/Location. Перенос
существующего Device требует плана: до/после для Device.site, Cluster.scope,
placement затронутых VM и целевых настроек SourceConfig. Проверить общий кластер,
несколько Site, rack/location и совместимость всех затронутых объектов. Не менять
scope общего кластера ради одного хоста автоматически. Согласованное обновление
настроек источника и проверка claims предотвращают возврат старого Site расписанием.
Selectel не должен сам исправлять размещение хостов других провайдеров.

### Автоматическая подготовка схемы NetBox

Ручное создание custom fields не требуется. Использовать версионированный
allowlist-манифест установщика: недостающие поля создаются автоматически,
повторный запуск ничего не меняет. Несовместимые type/object_types/ограничения
дают ошибку preflight до записи инвентаря; существующие значения не уничтожаются.
API-ключи/пароли и полные ответы API не сохранять в custom fields.

Начальный манифест: `selectel_refs` (JSON, скрытая проекция подтверждённых связей)
и `selectel_summary` (text, читаемая сводка), для Device/VirtualMachine, группа
Selectel. Постоянные bindings и права полей — отдельные модели, не JSON-замок.
Для стандартных свойств использовать штатные поля NetBox. Остальные услуги
сохраняются в модели инвентаря, без custom field на каждый ключ API.

В текущем шаге реализован **план схемы**, а не выполнение миграции:
`tools/selectel_audit/field_contract.py` проверяет create/unchanged/conflict;
отчёт показывает иерархию и матрицу полей. Экспорт custom fields пока не собирается,
поэтому отчёт честно указывает schema_status=not_checked. Автоматический bootstrap
надо подключить к установке Guard вместе с моделями и проверкой прав до первого
разрешённого apply. Ни миграция, ни field claims, ни новый writer пока не включены.

### Доступ по расписанию

Постоянное подключение использует сервисного пользователя с правами чтения и
secret broker; новые IAM-токены получаются автоматически по expires_at и после
перезапуска. Один повтор чтения после 401; 403 не повышает права. Ручной IAM-токен
допустим для текущего аудита, но не обещает бессрочную работу. Статический X-Token
не заменяет IAM для cloud/dedicated/current DNS. Отказ доступа сохраняет последний
снимок и отмечает его устаревшим. MFA личного пользователя остаётся включённой.

## Единица подключения и интерфейс

Отдельный раздел «Интеграции → Selectel». Карточка аккаунта: понятное имя,
проверенный номер аккаунта, статус доступа, время последнего сбора, охваченные
проекты/регионы, количество ресурсов и конфликтов. Несколько аккаунтов не смешивать.

Мастер: «Подключение → Проверка доступа → Область сбора → Выгрузка → Сопоставление».
Поля подключения: название, номер аккаунта, способ доступа (сервисный пользователь
для постоянной работы; временный IAM-токен для аудита), имя/пароль либо токен.
Секрет после сохранения не возвращается в UI. Права доступа проверяются по операциям
чтения нужных продуктов; успешный логин не означает полный доступ ко всем ресурсам.

На карточке: вкладки «Обзор», «Облачные VM», «Выделенные серверы», «Сети и адреса»,
«Другие услуги», «Сопоставление», «История». Виден результат каждой попытки чтения,
а не только зелёная галочка авторизации. Расписание синхронизации сначала выключено.
Действия «Собрать данные» и «Построить план NetBox» отделены от «Применить».

У кандидата показывать обе записи рядом, тип объекта, аккаунт/проект/регион,
публичные/приватные/floating адреса, доказательства совпадения, противоречия и
владельца каждого поля. Кнопки решения: «Связать», «Создать отдельно», «Игнорировать»,
«Разобрать конфликт». Решение сохраняется с автором, временем и версиями снимков;
перед применением перечитываются обе стороны.

## Модель данных приложения

Это интеграция аккаунта поверх существующих гипервизорных источников, а не
маскировка Selectel под ESXi/Proxmox. Текущий SourceConfig и регистрация требуют
хостовых параметров и не должны заставлять пользователя придумывать гипервизор
публичного облака. Предпочтительно добавить account/snapshot/binding модель:

- provider account: внутренний UUID, provider, проверенный domain/account ID,
  display name, ссылки на credentials, включённые продукты/проекты/регионы;
- snapshot: account, run ID, начало/конец, версия сборщика, coverage и записи;
- binding: составной provider key, NetBox content type/ID, решение и доказательства,
  автор решения, версия, разрешённые поля; уникальность в обе стороны внутри роли;
- proposal/conflict: предлагаемое изменение, причина, версия плана, разрешение.

Идентичность: provider + account ID + project ID + region + object kind + native ID.
Для dedicated первичен UUID ресурса в аккаунте; hw_uuid — отдельное свойство, не
обязательно равное DMI/BIOS UUID. Для VM первичен Nova UUID; для NIC — Neutron port
UUID; для диска — Cinder volume UUID. Имена, MAC, IP и тариф не являются ключами.

Один физический Device может иметь основной источник ESXi/Proxmox и дополнительную
связь с dedicated Selectel. Связь не должна переводить существующий объект в новое
владение или переписывать sync_identities текущего источника. Удаление аккаунта
Selectel или исчезновение его ресурса не удаляет VM/Device, управляемые гипервизором.

## Предварительная матрица полей

| Объект/поле | Источник | Куда/правило |
|---|---|---|
| Account/project native ID и имя | IAM | Собственная модель интеграции; связь с Tenant только после явного выбора, не Tenant на каждый аккаунт автоматически |
| Region/AZ/location UUID | Каталог/Nova/Dedicated | Сначала справочник провайдера; подтверждённое отображение в существующие Region/Site/ClusterGroup; не создавать физический Site по догадке |
| Dedicated UUID, hw_uuid, состояние заказа | Dedicated resource | Дополнительная связь с Device и provider metadata; оплачено/заблокировано не равно online/offline гипервизора |
| Manufacturer/model/serial | Только достоверные hardware данные | Заполнять пустые подтверждённые поля Device; config_name не превращать автоматически в DeviceType/model |
| Имя Device и management IP | ESXi/Proxmox/оператор | Сохранять; Selectel user_desc — отдельная подпись провайдера |
| Cloud VM UUID/name/status | Nova | VM в подтверждённом логическом кластере проекта/региона; физический Device необязателен; статусы map явно, неизвестные — на проверку |
| vCPU/RAM | Nova flavor/detail | vcpus и memory после проверки единиц; неизвестное значение не заменять нулём |
| Корневой/временный диск | Flavor + boot mode | Не складывать с Cinder boot volume дважды; отдельное происхождение/тип |
| Volume UUID, size, attachments | Cinder | VirtualDisk только при однозначной принадлежности; multiattach — отдельная связь/конфликт, не дублирование размера |
| Port UUID/MAC/admin state | Neutron | VMInterface; именование стабильно по port UUID, отображаемое имя отдельно |
| Fixed IP/subnet/network | Neutron | IPAddress в заранее подтверждённом VRF/scope; маска из subnet CIDR, не предположение /24 |
| Floating IP и NAT связь | Neutron | Отдельное отношение public ↔ fixed/port; не назначать floating IP напрямую NIC без согласованной модели |
| Public dedicated IP | Dedicated IPAM | Сохранить связь resource/network/subnet; primary IP только после согласованного правила и проверки существующего primary |
| Prefix/VLAN/VRF | Neutron/Dedicated | Предлагать создание по выбранной политике области; существующие совпадения CIDR/VLAN без scope не объединять |
| Тариф/оплачено до/допуслуги | Dedicated | Отдельный provider block; не перегружать технические поля NetBox |
| S3/DNS/LB/прочие услуги | Их API | Инвентаризация интеграции; не создавать фиктивные Device или VM для каждого продукта |

Уже принадлежащие ESXi/Proxmox VM сохраняют их CPU/RAM/диски/интерфейсы как основной
источник. Для cloud VM без другого владельца эти поля может вести Selectel после
принятия связи. Manual поля остаются вне allowlist. При смене источника требуется
отдельная явная операция передачи владения, а не совпадение имени.

## Правила сопоставления

1. Принятая ранее binding по неизменному provider key — основание для повторного
   поиска; подтвердить, что объект существует, тип верен и binding не дублирован.
2. Документированный общий аппаратный ID/serial может дать сильное доказательство
   для dedicated ↔ Device, но семантику IDs нужно проверить по снимку обеих сторон.
3. Полное имя/FQDN, публичный IP, MAC — подсказки. Учитывать NAT, VIP, DHCP,
   переиспользование адресов, шаблоны/клонирование VM. Не выполнять автоматический
   DNS resolve в идентичность; DNS-результат меняется и не доказывает владение.
4. Частный IP сравнивается только внутри заранее сопоставленных сетевых областей
   (account/project/network ↔ VRF/namespace). Даже одинаковый CIDR не доказывает одну сеть.
5. Противоречие стабильных IDs, несколько кандидатов, разные типы объектов,
   межаккаунтное совпадение или два претендента — конфликт. Не выбирать первый ответ.
6. Только имя или только IP никогда не дают автоматическую привязку. Отсутствие
   кандидата при неполном чтении не даёт разрешения на создание.

Нормализовать пробелы/регистр и завершающую DNS-точку лишь в ключе сравнения;
оригиналы показывать отдельно. Не удалять доменные суффиксы, цифры и разделители
для автоматического объединения. Не перетаскивать IP/MAC с чужих интерфейсов.

## Представление в NetBox

На существующем Device/VM отдельный блок «Selectel»: аккаунт, проект, регион,
тип/ID ресурса, статус провайдера, последнее наблюдение, состояние связи,
основание привязки и ссылка на карточку в Sync. Принятая связь визуально отличается
от кандидата; устаревший снимок и конфликт видны явно. Сырые JSON доступны только
в диагностике с соответствующими правами, не основной информационной таблицей.

Кандидатные API-only custom fields: `selectel_refs` и `selectel_observed_at` либо
таблица расширения Guard. Окончательный выбор после проверки версии NetBox,
текущего Guard и существующих custom fields. Значения refs должны содержать
только проверенные ID/состояние связи; секреты и полные API payload туда не попадают.
Детальное поле refs не создаётся до утверждения модели и миграции.

## Автоматическое создание и запуск

На этапе аудита автоматически создаются только локальные файлы отчёта. Затем:
выгрузка двух аккаунтов → разбор coverage → карта полей/реальных совпадений →
read-only Selectel UI/снимки → принятые bindings → проверяемый план → применение
на тестовом NetBox. Отдельно проверяется обновление Guard; не заменять его по
одному сходству тегов Sync.

Первый write этап должен уметь создать подтверждённые новые VM/интерфейсы/диски
и недостающие справочники только из показанного плана и allowlist. Никаких удалений
из обычного inventory; исчезнувшие записи сохраняются с last_seen и coverage.
401/403, пропущенный регион, неполная пагинация не считаются исчезновением.
Preflight, fingerprint свежего плана, блокировка применения, аудит и идемпотентность
используют существующие механизмы Sync. Дополнительный слой Selectel не должен
позволять обойти проверки NetBox Guard.

## Приёмка по реальным данным

- Сверить видимые проекты/числа cloud VM и dedicated ресурсов с панелью обоих
  аккаунтов; объяснить каждый пробел или фильтр прав. Не считать скриншоты полным списком.
- Выбрать пары: арендованный ESXi, арендованный Proxmox, cloud VM; сравнить IDs,
  hostname, реальные интерфейсы/адреса, NAT и текущие поля NetBox.
- Проверить одинаковые имена, повтор private IP в разных проектах, смену имени,
  пересоздание VM с новым UUID, IP reallocation, два аккаунта и неверный токен.
- Провал страницы/проекта должен сохранять частичный снимок и блокировать
  выводы об отсутствии/удалении; перестановка страниц не создаёт дубликатов.
- После применения повторный план без изменений; ручные поля и прежние владельцы
  не меняются; ни одна write-операция не обращается к production.
